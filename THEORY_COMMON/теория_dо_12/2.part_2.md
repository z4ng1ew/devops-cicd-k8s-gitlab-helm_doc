# Теория: что такое Helm и зачем он нужен

## Главная аналогия

Helm — это **`apt` для Kubernetes**. То есть **менеджер пакетов**.

Когда ты ставишь nginx на Ubuntu, ты пишешь `apt install nginx`. apt идёт в репозиторий, скачивает пакет (`.deb`), распаковывает, запускает скрипты установки. **Пакет** — это упакованная программа с инструкциями: что куда положить, какие зависимости нужны.

Helm делает то же самое для Kubernetes. Только пакет здесь называется **chart** (чарт), и вместо `apt install` пишешь `helm install`.

## Зачем это нужно

В DO11 ты руками применил 13 манифестов. Это сработало, но если завтра ты захочешь:
- развернуть это же приложение **в другом кластере** — нужно переписать все хосты, ip, sa
- развернуть **второй экземпляр** того же приложения для тестов — нужно скопировать всё и поменять имена
- сделать `rollback` к предыдущей версии после плохого обновления — нет команды, надо вручную возвращать манифесты

Helm решает все три проблемы одним приёмом — **шаблонизацией** (templating).

## Шаблонизация — что это

Шаблон — это YAML с **«пропусками»** в фигурных скобках:

```yaml
# Шаблон
replicas: {{ .Values.replicaCount }}

# Файл values.yaml
replicaCount: 3

# Результат после рендеринга
replicas: 3
```

Helm видит `{{ ... }}` и подставляет туда значение из `values.yaml`. Это и называется **рендеринг** (rendering — отрисовка).

## Ключевые понятия (запоминай — спросят на проверке)

| Термин | Что это | Пример |
|---|---|---|
| **Chart** | Папка с шаблонами + метаданными. **Единица упаковки**. | `hotels-app/` |
| **Chart.yaml** | Метаданные чарта: имя, версия, описание. | `name: hotels-app, version: 0.1.0` |
| **values.yaml** | Значения для подстановки в шаблоны. **Все настройки**. | `replicaCount: 3` |
| **templates/** | Папка с YAML-шаблонами. Здесь все Deployment, Service, Ingress. | `templates/deployment.yaml` |
| **Release** | Конкретная установка чарта в кластере. Имеет имя. | `my-hotels` |
| **Revision** | Номер версии релиза. Растёт после каждого `helm upgrade`. | `REVISION: 2` |
| **`helm install`** | Создать новый релиз из чарта. | `helm install my-hotels ./hotels-app` |
| **`helm upgrade`** | Обновить существующий релиз. | `helm upgrade my-hotels ./hotels-app` |
| **`helm rollback`** | Откатить релиз к предыдущей ревизии. | `helm rollback my-hotels 1` |
| **`helm package`** | Упаковать чарт в `.tgz`-архив. | `helm package ./hotels-app` |
| **`helm template`** | Отрендерить шаблоны и вывести без применения. | `helm template ./hotels-app` |
| **`helm lint`** | Проверить чарт на синтаксические ошибки. | `helm lint ./hotels-app` |

## Helm vs Kustomize — отличие в одном предложении

**Helm** использует **шаблонный синтаксис** `{{ }}` для подстановки значений. **Kustomize** работает только с **обычным YAML** + патчи поверх.

То есть Helm — это «программирование» в шаблонах, Kustomize — «декларативные правки» к готовым манифестам. Оба валидны, выбор зависит от задачи.

# Шаг 3. Пишем `values.yaml`

Это **сердце Helm-чарта**. Сюда выносим всё, что может меняться. Откроем редактором или перепишем через `cat`:

```bash
cd ~/do_12/src/hotels-app

cat > values.yaml << 'EOF'
# values.yaml - значения для подстановки в шаблоны.
# Меняя эти значения, можно настроить приложение под разные окружения.

# Количество реплик для каждого сервиса
replicaCount:
  postgres: 1
  rabbitmq: 1
  session: 1
  hotel: 1
  booking: 1
  payment: 1
  loyalty: 1
  report: 1
  gateway: 1

# Настройки образов
image:
  pullPolicy: Never
  postgres: src-postgres:latest
  rabbitmq: rabbitmq:3.12-management-alpine
  session: src-session-service:latest
  hotel: src-hotel-service:latest
  booking: src-booking-service:latest
  payment: src-payment-service:latest
  loyalty: src-loyalty-service:latest
  report: src-report-service:latest
  gateway: src-gateway-service:latest

# Настройки Ingress
ingress:
  enabled: true
  sessionHost: session.10.174.8.95.nip.io
  gatewayHost: gateway.10.174.8.95.nip.io
  tlsSecret: wildcard-nipio-tls
  clusterIssuer: my-ca-issuer
EOF
```

**Объяснение структуры `values.yaml`**:
- `replicaCount.gateway` — внутри шаблона доступ через `{{ .Values.replicaCount.gateway }}`
- `image.postgres` — через `{{ .Values.image.postgres }}`
- Иерархия в YAML = иерархия через точку в шаблоне

📸 **СКРИНШОТ**: `cat values.yaml`.

# Шаг 4. Превращаем манифесты в шаблоны

Сейчас в `templates/` лежат **обычные YAML-файлы**, без переменных. Чтобы Helm подставлял в них значения, нужно заменить **захардкоженные** места на `{{ .Values.* }}`.

Главные замены:
- `replicas: 1` → `replicas: {{ .Values.replicaCount.gateway }}` (и так для каждого сервиса)
- `image: src-gateway-service:latest` → `image: {{ .Values.image.gateway }}`
- `imagePullPolicy: Never` → `imagePullPolicy: {{ .Values.image.pullPolicy }}`

**Делаем это скриптом, чтобы не править руками 11 файлов:**

```bash
cd ~/do_12/src/hotels-app/templates

# Соответствие "префикс файла" -> "ключ в values"
declare -A SVCMAP=(
  ["04-postgres"]="postgres"
  ["05-rabbitmq"]="rabbitmq"
  ["06-session-service"]="session"
  ["07-hotel-service"]="hotel"
  ["08-booking-service"]="booking"
  ["09-payment-service"]="payment"
  ["10-loyalty-service"]="loyalty"
  ["11-report-service"]="report"
  ["12-gateway-service"]="gateway"
)

for file_prefix in "${!SVCMAP[@]}"; do
  svc="${SVCMAP[$file_prefix]}"
  file="${file_prefix}.yaml"
  if [ -f "$file" ]; then
    # Заменяем образ (вариант 1: src-<имя>-service:latest)
    sed -i "s|image: src-${svc}-service:latest|image: {{ .Values.image.${svc} }}|g" "$file"
    # Образ postgres
    sed -i "s|image: src-postgres:latest|image: {{ .Values.image.postgres }}|g" "$file"
    # Образ rabbitmq
    sed -i "s|image: rabbitmq:3.12-management-alpine|image: {{ .Values.image.rabbitmq }}|g" "$file"
    # imagePullPolicy
    sed -i "s|imagePullPolicy: Never|imagePullPolicy: {{ .Values.image.pullPolicy }}|g" "$file"
    # replicas: 1 (только первое вхождение в файле - это в Deployment)
    sed -i "0,/replicas: 1/{s|replicas: 1|replicas: {{ .Values.replicaCount.${svc} }}|}" "$file"
    echo "✓ обработан $file"
  fi
done

# Проверим, что получилось
cat 12-gateway-service.yaml | head -20
```

Должны увидеть `{{ .Values.image.gateway }}` и `{{ .Values.replicaCount.gateway }}`.

📸 **СКРИНШОТ**: `cat 12-gateway-service.yaml` — видны `{{ ... }}`.

# Шаг 5. Переписываем Ingress на шаблон

Этот файл сложнее, поэтому перезапишем целиком:

```bash
cd ~/do_12/src/hotels-app/templates

cat > 13-app-ingress.yaml << 'EOF'
{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
  annotations:
    cert-manager.io/cluster-issuer: {{ .Values.ingress.clusterIssuer }}
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - {{ .Values.ingress.sessionHost }}
        - {{ .Values.ingress.gatewayHost }}
      secretName: {{ .Values.ingress.tlsSecret }}
  rules:
    - host: {{ .Values.ingress.sessionHost }}
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: session-service
                port:
                  number: 8081
    - host: {{ .Values.ingress.gatewayHost }}
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: gateway-service
                port:
                  number: 8087
{{- end }}
EOF
```

Поясняю новый синтаксис:
- `{{- if .Values.ingress.enabled }}` — **условный блок**. Если в `values.yaml` написано `ingress.enabled: false`, весь блок до `{{- end }}` пропустится, и Ingress не создастся. Это **мощный приём**: одним флагом включаем/выключаем целые куски.
- Дефис `-` в `{{-` убирает пустую строку, которая появляется в результате. Это косметика.

# Шаг 6. Правим `Chart.yaml`

```bash
cd ~/do_12/src/hotels-app

cat > Chart.yaml << 'EOF'
apiVersion: v2
name: hotels-app
description: Helm chart for Hotels microservices application (DO12)
type: application
version: 0.1.0
appVersion: "1.0.0"
EOF
```

Объясняю:
- `apiVersion: v2` — современная схема Helm 3 (`v1` была у Helm 2)
- `version` — **версия чарта**. Меняется при правке шаблонов.
- `appVersion` — **версия самого приложения**, которое чарт разворачивает. Независимая от `version`.
- `type: application` — обычное приложение (есть ещё `library` — библиотечный чарт без шаблонов)

# Шаг 12. Обновление через `helm upgrade`

Пункт 9 методички: «Внести как минимум одно изменение в `values.yaml` и выполнить `helm upgrade`».

Меняем количество реплик gateway с 1 на 2:

```bash
cd ~/do_12/src/hotels-app

# Заменяем значение
sed -i 's|  gateway: 1$|  gateway: 2|' values.yaml

# Проверим, что изменилось
grep -A 1 "replicaCount:" values.yaml | head -3
```

Применяем обновление. **Важно**: Helm-апгрейд берёт чарт из папки, не из `.tgz` — поэтому передаём путь к папке:

```bash
cd ~/do_12/src

helm upgrade my-hotels ./hotels-app --namespace hotels
```

Helm покажет `REVISION: 2`.

Проверяем:
```bash
kubectl get deployment gateway-service -n hotels
```

Должно показать `READY 2/2`.

📸 **СКРИНШОТ для пункта 9**: `helm upgrade` + `kubectl get deployment gateway-service -n hotels` — теперь 2 реплики.

История релизов:
```bash
helm history my-hotels -n hotels
```

📸 **СКРИНШОТ**: история — `REVISION 1` (deployed → superseded) и `REVISION 2` (deployed).

`superseded` (вытесненный) — статус старой ревизии. Helm их хранит, чтобы можно было откатиться через `helm rollback my-hotels 1 -n hotels`.

# Что готовить к защите (вопросы от пира)

| Вопрос | Идея ответа |
|---|---|
| «Чем Helm лучше Kustomize?» | Они решают разные задачи. Helm — пакетный менеджер, упаковывает приложения для дистрибуции (например, готовые чарты Prometheus, Grafana). Kustomize — для управления окружениями одного приложения. Я показал в проекте оба подхода на одном и том же приложении. |
| «Что такое REVISION?» | Helm хранит каждое состояние релиза в Secret-объекте внутри кластера (`sh.helm.release.v1.my-hotels.v1`). При `helm upgrade` создаётся новая ревизия, старая помечается `superseded`. По ревизии можно откатиться через `helm rollback`. |
| «Что значит `{{- if .Values.ingress.enabled }}`?» | Это **условный блок** в Go-шаблонах (Helm использует Go templating). Если значение `ingress.enabled` в values.yaml `true` — блок отрендерится. Если `false` — блок вырежется, Ingress не создастся. Дефис `-` убирает пустую строку из вывода. |
| «Чем `helm install` отличается от `helm template`?» | `template` только рендерит шаблоны и выводит результат в терминал. Кластер не трогает. `install` рендерит **и** применяет результат к кластеру, плюс создаёт запись о релизе. |
| «Что лежит в `Chart.yaml`?» | Метаданные чарта: имя (`name`), версия чарта (`version`), версия приложения (`appVersion`), описание. `version` и `appVersion` независимы: можно правки в шаблоны = `version` растёт, а само приложение прежнее. |
| «Что делает `helm lint`?» | Проверяет чарт на синтаксические ошибки: правильность Go-шаблонов, валидность YAML после рендеринга, наличие обязательных полей в Chart.yaml. |
| «Что в `.helmignore`?» | Аналог `.gitignore` или `.dockerignore`. При `helm package` все файлы, перечисленные в `.helmignore`, не попадут в `.tgz`. Например, бэкапы, временные файлы. |
| «Зачем `helm create`, если можно вручную создать структуру?» | Это **best-practice**: гарантирует правильную структуру, генерирует `_helpers.tpl` с typical-функциями (полное имя, селекторы), готовый `NOTES.txt`. Можно и вручную, но `helm create` экономит время. |
