# Что такое Helm и Kustomize — на простых аналогиях

## Аналогия первая: рецепт борща

Представь, что твои манифесты из DO11 — это **рецепт борща**. У тебя 13 шагов. Завтра ты хочешь сварить такой же борщ, но **на больше людей** (увеличить количество свёклы вдвое) и **с другой солью** (заменить морскую на йодированную).

Что делать?

**Вариант «копировать»:** перепишешь весь рецепт от начала до конца, поменяешь два числа. Потом ещё раз. И ещё раз. Через месяц у тебя 10 рецептов почти-одного-и-того-же борща, и ты не помнишь, где какая версия. **Это твой DO11.** Работает, но если завтра захочешь развернуть приложение второй раз для тестов — надо копировать всю папку и править руками.

**Вариант Helm:** ты пишешь **один рецепт-шаблон с пропусками**:
> «Положить ___ грамм свёклы, посыпать ___ солью.»

И отдельный файл `values.yaml` (значения):
> Свёкла = 500г, соль = морская.

Когда варишь — выполняешь команду `helm install`, и шаблон **автоматически заполняется** значениями. Хочешь другой борщ? Поменяй только `values.yaml`. Helm — **это шаблонизатор + менеджер пакетов** (как `apt` в Linux, только для k8s).

**Вариант Kustomize:** у тебя есть **базовый рецепт без изменений** (`base/`). Дополнительно — папка `overlays/production/` со словами: «А в production-версии увеличь свёклу до 1кг и замени соль». Kustomize не использует шаблоны (`{{ ... }}`), он **накладывает патчи** (правки) на исходный рецепт. Никакого синтаксиса. Просто YAML, который говорит «возьми это, замени там, добавь сюда».

## Когда что используют

| Инструмент | Когда полезен | Минус |
|---|---|---|
| **Helm** | Готовые приложения для дистрибуции (PostgreSQL, nginx, Grafana — кто-то написал чарт, мы устанавливаем) | Шаблонный синтаксис `{{ }}` — это «ещё один язык», его надо учить |
| **Kustomize** | Свои приложения в разных окружениях (dev/staging/prod) | Сложнее писать многослойные перекрытия |

В реальности часто **используют оба сразу**: Helm — для сторонних приложений, Kustomize — для своих. По заданию мы научимся **обоим**, на одном и том же приложении.

# Перед стартом — несколько ключевых терминов

Дам тебе словарь, чтобы не утонуть. Возвращайся сюда, если встретится незнакомое слово.

**Манифест** — YAML-файл с описанием объекта Kubernetes (Deployment, Service и т.д.). У нас их 13 из DO11.

**Шаблон (template)** — YAML-файл с «пропусками» в виде `{{ .Values.something }}`. Помечен фигурными скобками. Когда Helm видит такой файл, он заменяет `{{ }}` на значение из `values.yaml`.

**Values (values.yaml)** — файл со значениями для подстановки в шаблоны. Это «настройки» приложения.

**Чарт (chart)** — папка с метаданными (`Chart.yaml`), значениями (`values.yaml`) и шаблонами (`templates/`). Это **единица упаковки** в Helm.

**Релиз (release)** — конкретная установка чарта в кластере. Один чарт можно установить несколько раз с разными именами и параметрами → получится несколько релизов.

**Overlay (оверлей, накладка)** — в Kustomize: папка, которая «накладывается» поверх `base/` и модифицирует его.

**Патч (patch)** — конкретное изменение, которое Kustomize применяет. Например: «увеличь количество реплик до 3».

**namespace (неймспейс, пространство имён)** — изолированная зона в Kubernetes. У нас сейчас всё в `default`, у мониторинга — в `monitoring`. Можно думать как о папках.

# 📦 Part 1. Kustomize

## Шаг 1: установка Kustomize

В `kubectl` уже встроен Kustomize (с версии 1.14), но для отчёта правильнее установить отдельно — так требует методичка.

```bash
# Скачиваем установщик
curl -s "https://raw.githubusercontent.com/kubernetes-sigs/kustomize/master/hack/install_kustomize.sh" | bash

# Переносим в системный PATH (чтобы команда работала из любой папки)
sudo mv kustomize /usr/local/bin/

# Проверяем
kustomize version
```

📸 **СКРИНШОТ**: `kustomize version` — версия установлена.

## Шаг 2: создаём структуру папок

Методичка прямо указывает структуру. Делаем её:

```bash
cd ~/DO-12/src
mkdir -p kustomize/base
mkdir -p kustomize/overlays/production

# Проверим

```

Должно быть:
```
kustomize/
├── base/
```

**Логика структуры**:

- `overlays/production/` — «накладка», специфичная для production: продакшен-секреты, увеличенное число реплик, ресурсные лимиты

## Шаг 4: пишем `base/kustomization.yaml`

Это **главный файл Kustomize**. Он говорит: «вот эти YAML-файлы — части моей базы».

```bash
cd ~/DO-12/src/kustomize/base

cat > kustomization.yaml << 'EOF'
# kustomization.yaml — главный файл Kustomize
# Перечисляет все YAML-файлы, которые входят в эту "базу"
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

# Список манифестов, входящих в базу
resources:
  - 03-postgres-pv.yaml
  - 04-postgres.yaml
  - 05-rabbitmq.yaml
  - 06-session-service.yaml
  - 07-hotel-service.yaml
  - 08-booking-service.yaml
  - 09-payment-service.yaml
  - 10-loyalty-service.yaml
  - 11-report-service.yaml
  - 12-gateway-service.yaml
  - 13-app-ingress.yaml
EOF
```

Объясняю: `apiVersion` и `kind` — обязательные «маркеры», что это файл Kustomize. `resources` — список файлов, которые нужно объединить. Кустомайз их склеит и применит к кластеру всё сразу.

## Шаг 5: создаём `replicas-patch.yaml`

Это **патч** — частичный YAML, который говорит «найди ресурс `gateway-service` и поменяй в нём количество реплик на 3».

```bash
cd ~/DO-12/src/kustomize/overlays/production

cat > replicas-patch.yaml << 'EOF'
# replicas-patch.yaml — патч, увеличивающий gateway до 3 реплик
# Это не полный манифест, а только те поля, которые меняем
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gateway-service
spec:
  replicas: 3
EOF
```

**Важно**: в патче указываем **только то, что меняем**. Kustomize объединит этот патч с полным манифестом из `base/12-gateway-service.yaml`.

## Шаг 6: пишем `overlays/production/kustomization.yaml`

Этот файл — главный для оверлея. Он говорит: «возьми базу, добавь ConfigMap и Secret, примень патч».

```bash
cd ~/DO-12/src/kustomize/overlays/production

cat > kustomization.yaml << 'EOF'
# Оверлей production: накладывается поверх базовой конфигурации
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

# Берём базовую конфигурацию
resources:
  - ../../base
  - 01-configmap.yaml
  - 02-secrets.yaml

# Накладываем патчи
patches:
  - path: replicas-patch.yaml
    target:
      kind: Deployment
      name: gateway-service
EOF
```

Расшифровка:
- `resources` — берём всё из `../../base` (путь относительный — две точки означают «папка выше», то есть `kustomize/`, потом `base/`)
- Плюс добавляем ConfigMap и Secret из текущей папки
- `patches` — список патчей. У нас один — увеличить реплики gateway до 3.

## Шаг 7: пишем корневой `kustomization.yaml` (опционально)

По методичке нужен ещё один файл в корне проекта Kustomize:

```bash
cd ~/DO-12/src/kustomize
```

## Шаг 5: правим шаблоны для использования values

В Helm-шаблонах используется синтаксис `{{ .Values.something }}`. Это означает «подставь сюда значение из `values.yaml`».

Покажу на примере `gateway-service`. Открой `templates/12-gateway-service.yaml`:

Найди строки:
```yaml
spec:
  replicas: 1
```

Замени на:
```yaml
spec:
  replicas: {{ .Values.replicaCount.gateway }}
```

И:
```yaml
          image: src-gateway-service:latest
          imagePullPolicy: Never
```

на:
```yaml
          image: {{ .Values.image.gateway }}
          imagePullPolicy: {{ .Values.image.pullPolicy }}
```

**Чтобы не править руками 11 файлов** — вот скрипт, который сделает это автоматически:

```bash
cd ~/DO-12/src/hotels-app/templates

# Заменяем replicas: 1 → шаблонизированное значение для каждого сервиса
declare -A SVCMAP=(
  ["04-postgres"]="postgres"
  ["05-rabbitmq"]="rabbitmq"
  ["06-session-service"]="session"
  ["07-hotel-service"]="hotel"
  ["08-booking-service"]="booking"
  ["09-payment-service"]="payment"
  ["10-loyalty-service"]="loyalty"
  ["11-report-service"]="report"
  ["12-gateway-service"]="gateway"
)

for file_prefix in "${!SVCMAP[@]}"; do
  svc="${SVCMAP[$file_prefix]}"
  file="${file_prefix}.yaml"
  if [ -f "$file" ]; then
    # Заменяем образ
    sed -i "s|image: src-${svc}-service:latest|image: {{ .Values.image.${svc} }}|g" "$file"
    sed -i "s|image: src-postgres:latest|image: {{ .Values.image.postgres }}|g" "$file"
    sed -i "s|image: rabbitmq:3.12-management-alpine|image: {{ .Values.image.rabbitmq }}|g" "$file"
    # Заменяем imagePullPolicy
    sed -i "s|imagePullPolicy: Never|imagePullPolicy: {{ .Values.image.pullPolicy }}|g" "$file"
    # Заменяем replicas: 1 (только первое вхождение в файле)
    sed -i "0,/replicas: 1/{s|replicas: 1|replicas: {{ .Values.replicaCount.${svc} }}|}" "$file"
    echo "✓ Обработан $file"
  fi
done
```

Проверим, что получилось в одном из файлов:

```bash

```

Должны увидеть `{{ .Values.image.gateway }}` и `{{ .Values.replicaCount.gateway }}`.

## Шаг 6: правим Ingress на использование values

```bash

  name: app-ingress
  annotations:
    cert-manager.io/cluster-issuer: {{ .Values.ingress.clusterIssuer }}

  ingressClassName: nginx
  tls:
    - hosts:
        - {{ .Values.ingress.sessionHost }}
        - {{ .Values.ingress.gatewayHost }}
      secretName: {{ .Values.ingress.tlsSecret }}
  rules:
    - host: {{ .Values.ingress.sessionHost }}
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: session-service
                port:
                  number: 8081
    - host: {{ .Values.ingress.gatewayHost }}
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: gateway-service
                port:
                  number: 8087
{{- end }}
EOF
```

Здесь `{{- if .Values.ingress.enabled }}` — это **условный блок**. Если в `values.yaml` написано `ingress.enabled: false`, Ingress вообще не создастся. Это полезно для тестов без TLS.

## Шаг 12: обновление через `helm upgrade`

Методичка просит внести изменение в `values.yaml` и сделать `helm upgrade`. Сделаем — увеличим количество реплик gateway:

```bash
cd ~/DO-12/src/hotels-app

# Открой values.yaml в редакторе
# Найди в replicaCount:
#   gateway: 1
# Поменяй на:
#   gateway: 2

# Или sed-ом:
sed -i 's|  gateway: 1|  gateway: 2|' values.yaml

# Проверим
grep "gateway:" values.yaml
```

Применяем обновление:

```bash
cd ~/DO-12/src

helm upgrade my-hotels ./hotels-app --namespace hotels

# Проверим, что реплик стало 2
kubectl get deployment gateway-service -n hotels
```

📸 **СКРИНШОТ**: `kubectl get deployment -n hotels` — у gateway-service `READY 2/2`.

История релизов:

```bash
helm history my-hotels -n hotels
```

📸 **СКРИНШОТ**: история — `REVISION 1` и `REVISION 2`.

Если что-то пойдёт не так — `helm rollback my-hotels 1 -n hotels` вернёт первую версию. **Это и есть главный плюс Helm над просто `kubectl apply`** — версионирование релизов.

# Что подготовить для защиты

После DO11 ты знаешь, на что обращают внимание ревьюеры. Готовьсь к таким вопросам:

| Вопрос | Идея ответа |
|---|---|
| «Почему ты использовал Kustomize, а не Helm для одного приложения?» | Они решают разные задачи. Kustomize — для управления окружениями (dev/staging/prod) **одного приложения**. Helm — для упаковки и дистрибуции готовых приложений. В заданий показал оба. |
| «Чем `kubectl apply -k` отличается от `kubectl apply -f`?» | `-k` рендерит через Kustomize (склеивает base + overlay), `-f` применяет готовый YAML напрямую. |
| «Чем `helm template` отличается от `helm install`?» | `template` рендерит шаблоны и выводит на экран без применения к кластеру. `install` рендерит и применяет. `template` полезен для отладки. |
| «Что такое `_helpers.tpl`?» | Файл со вспомогательными функциями-«макросами» в Helm. Например, `{{ include "myapp.fullname" . }}` вернёт сгенерированное имя. Мы его удалили, потому что не используем сложные имена. |
| «Зачем `version` и `appVersion` в Chart.yaml?» | `version` — версия **чарта** (повышается при изменении шаблонов). `appVersion` — версия **приложения** внутри чарта. Они независимы: можно обновить шаблоны, не обновляя приложение. |
| «Почему ты не использовал зависимости (dependencies) в Chart.yaml?» | Это для случая, когда твой чарт использует другие чарты как «подкомпоненты». Например, своё приложение + PostgreSQL чарт от Bitnami. У нас всё своё, поэтому зависимости не нужны. |
| «Какой алгоритм работает в `helm rollback`?» | Helm хранит **в кластере** Secret-объекты с каждой ревизией релиза (`sh.helm.release.v1.my-hotels.v1`, `v2` и т.д.). При rollback он берёт нужную ревизию и применяет её манифесты. |
