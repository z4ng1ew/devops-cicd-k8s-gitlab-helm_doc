## 📦 Pod (Под) — простыми словами

**Pod** (произносится «под», от англ. *pod* — «капсула», «стручок») — это **самая маленькая и простая единица в Kubernetes**, которую можно создать и запустить. Это «обёртка» для одного или нескольких контейнеров, которые работают вместе.

> 🧩 **Аналогия из жизни:**
> 
> Представь, что ты запускаешь приложение:
> 
> | Реальный мир | Мир Kubernetes |
> |-------------|---------------|
> | 🚗 Машина | **Node** (узел / сервер) |
> | 📦 Контейнер с грузом | **Container** (твой Docker-контейнер) |
> | 🚚 Паллета с одним или несколькими связанными контейнерами | **Pod** |
> 
> **Pod** — это как паллета: на ней может лежать один большой контейнер, или несколько маленьких, которые нужно везти вместе (например, приложение + логгер).

---

## 🔑 Главное, что нужно знать о Pod

| Факт | Что это значит |
|------|---------------|
| 🔹 **Один или несколько контейнеров** | Чаще всего — один. Но если два контейнера тесно связаны (например, приложение и помощник для сбора логов), их можно положить в один под |
| 🔹 **Общий «контекст»** | Все контейнеры в поде делят: сеть (один IP), хранилище (Volumes), настройки |
| 🔹 **Живёт недолго** | Поды **эфемерны** (временные). Если он упал — Kubernetes создаст новый, а не чинит старый |
| 🔹 **Не управляется напрямую** | Обычно ты создаёшь не сам под, а **контроллер** (Deployment, StatefulSet), который сам создаёт и следит за подами |

## 🧱 Из чего состоит Pod (упрощённо)

```yaml
apiVersion: v1
kind: Pod  # ← тип объекта: Под
metadata:
  name: my-app-pod  # ← имя пода
  labels:
    app: my-app     # ← метки для поиска и группировки
spec:
  containers:
  - name: nginx     # ← имя контейнера внутри пода
    image: nginx:1.24  # ← какой образ запускать
    ports:
    - containerPort: 80  # ← какой порт открыть внутри
    resources:
      requests:
        memory: "64Mi"   # ← сколько памяти гарантированно нужно
        cpu: "250m"      # ← сколько CPU (250 миллиядер)
      limits:
        memory: "128Mi"  # ← максимум памяти
        cpu: "500m"      # ← максимум CPU
  volumes:           # ← общее хранилище для контейнеров в поде
  - name: shared-data
    emptyDir: {}     # ← временная папка, живёт пока жив под
```

## 🌐 Сеть в Pod — как это работает

Все контейнеры внутри одного пода:

```
┌─────────────────────────────┐
│           Pod               │
│  IP: 10.244.1.15            │
│                             │
│  ┌─────────┐  ┌─────────┐  │
│  │Container│  │Container│  │
│  │   App   │  │ Logger  │  │
│  │ порт 80 │  │ порт 90 │  │
│  └────┬────┘  └────┬────┘  │
│       │           │        │
│       ▼           ▼        │
│  Оба видят:               │
│  • localhost:80  ← App    │
│  • localhost:90  ← Logger │
│  • Один IP на всех       │
└─────────────────────────────┘
```

> 💡 **Простыми словами:** Контейнеры в одном поде — как соседи по квартире. У квартиры один адрес (IP), но в каждой комнате (контейнере) свой номер порта.

## 🔄 Жизненный цикл Pod

```
1. Pending (Ожидание)
   → Под создан, но ещё не запущен (ждёт узел, образ, сеть)

2. Running (Работает)
   → Контейнер запущен, приложение отвечает

3. Succeeded (Успешно завершён)
   → Контейнер отработал и завершился с кодом 0 (для задач типа "выполни скрипт")

4. Failed (Ошибка)
   → Контейнер упал с ошибкой (код ≠ 0)

5. Unknown / CrashLoopBackOff
   → Неизвестное состояние или постоянные перезапуски из-за ошибок
```

### Проверить состояние подов:
```bash
kubectl get pods
# NAME         READY   STATUS    RESTARTS   AGE
# my-pod       1/1     Running   0          5m
```

## ❓ Почему не запускать контейнеры напрямую, без Pod?

Потому что **Pod — это «единица масштабирования и управления»**:

| Задача | Как решает Pod |
|--------|---------------|
| 🔹 Масштабирование | Kubernetes добавляет не «контейнеры», а **поды** (реплики) |
| 🔹 Обновление | При деплое создаются новые поды, старые удаляются — без простоя |
| 🔹 Отказоустойчивость | Если под упал — контроллер создаст новый на другом узле |
| 🔹 Сеть и хранилище | У пода свой IP и тома — контейнерам не нужно это настраивать |

> 🧠 **Запомни:** Ты почти никогда не работаешь с «голыми» подами. Ты создаёшь **Deployment**, а он уже управляет подами за тебя.

## 🛠️ Практика: как создать и посмотреть под

### 🔹 Создать простой под (для теста):
```bash
kubectl run test-pod --image=nginx:1.24 --restart=Never
```
- `--restart=Never` → создаёт именно **под**, а не деплоймент

### 🔹 Посмотреть поды:
```bash
kubectl get pods
# NAME       READY   STATUS    RESTARTS   AGE
# test-pod   1/1     Running   0          30s
```

### 🔹 Зайти внутрь пода (как `docker exec`):
```bash
kubectl exec -it test-pod -- /bin/bash
# Теперь ты внутри контейнера!
```

### 🔹 Посмотреть логи:
```bash
kubectl logs test-pod
```

### 🔹 Удалить под:
```bash
kubectl delete pod test-pod
```

## ⚠️ Важные нюансы

| Нюанс | Почему это важно |
|-------|---------------|
| 🔹 **Поды не «чинятся»** | Если приложение в поде упало — Kubernetes не перезапустит процесс внутри. Он **пересоздаст весь под** |
| 🔹 **Данные в поде временные** | Если под удалится — данные внутри контейнера пропадут. Для постоянного хранения нужны **PV / PVC** (о которых мы говорили раньше) |
| 🔹 **Один под = один узел** | Под не может «растянуться» на несколько серверов. Все его контейнеры живут на одной машине |
| 🔹 **Сеть между подами** | Каждый под получает свой IP. Поды могут общаться друг с другом напрямую по этому IP |

## 🧠 Коротко для запоминания

```
🔹 Pod = минимальная единица запуска в Kubernetes
🔹 Внутри: один (чаще) или несколько тесно связанных контейнеров
🔹 У пода: свой IP, общее хранилище, общие настройки сети
🔹 Поды временные: упал → создали новый, а не починили старый
🔹 Ты обычно управляешь подами через Deployment, а не напрямую
🔹 Команды: kubectl get pods, kubectl logs <pod>, kubectl exec -it <pod> -- bash
```

## ❓ Частые вопросы

**В: Можно ли в поде запустить два независимых приложения?**  
О: Технически — да. Но это плохая практика. Если приложения не связаны тесно — лучше разнести их по разным подам.

**В: Почему у пода свой IP, а не у контейнера?**  
О: Потому что под — единица сети в Kubernetes. Это упрощает маршрутизацию: не нужно отслеживать каждый контейнер, только поды.

**В: Что будет, если закончится место на узле, где работает под?**  
О: Kubernetes может «вытеснить» (evict) под на другой узел, если есть свободные ресурсы. Если нет — под перейдёт в статус `Pending`, пока ресурсы не освободятся.
