## ☁️ Что означает «cloud» в URL манифеста?

Ссылка:
```
.../deploy/static/provider/cloud/deploy.yaml
```

Слово **`cloud`** здесь указывает на **вариант развёртывания**, рассчитанный на облачные платформы (AWS, GCP, Yandex Cloud и т.д.), где есть встроенная поддержка сервиса типа `LoadBalancer`.

### В чём разница между вариантами?

| Вариант | Тип Service | Для чего предназначен |
|---------|-------------|----------------------|
| **`cloud`** | `type: LoadBalancer` | Облака, где провайдер автоматически выдаёт внешний IP |
| **`baremetal`** | `type: NodePort` | «Голое железо», домашние сервера, где нет облачного балансировщика |
| **`docker`** | `type: NodePort` | Локальные тесты в Docker Desktop |

### Почему нам подходит `cloud`, хотя у нас не облако?

Потому что **k3s включает в себя ServiceLB** (ранее klipper-lb) — это лёгкая реализация `LoadBalancer`, которая работает даже на обычных ВМ.

- Когда манифест создаёт `Service: LoadBalancer`, ServiceLB «видит» это и **сам назначает внешний IP** из доступного диапазона.
- Если бы мы взяли `baremetal`-версию, там был бы `NodePort` — и нам пришлось бы вручную настраивать проброс портов или ставить MetalLB.

> 🧠 **Простыми словами:** `cloud` в названии — это не про «обязательно Яндекс.Облако», а про «предполагается, что в кластере есть кто-то, кто умеет раздавать внешние IP для LoadBalancer». В k3s этот «кто-то» — встроенный ServiceLB.

## 🚪 LoadBalancer vs Ingress Controller: кто точка входа?

Ты абсолютно прав, что **Ingress Controller** — это логическая точка входа. Но давай уточним уровни:

### 📦 Два уровня входа в кластер

```
Интернет
   │
   ▼
┌─────────────────┐
│  LoadBalancer   │ ← Сетевой уровень (L4: TCP/UDP)
│  (Service)      │    «Какой порт открыть наружу?»
└────────┬────────┘
         │ трафик на порты 80/443
         ▼
┌─────────────────┐
│  Ingress        │ ← Прикладной уровень (L7: HTTP/HTTPS)
│  Controller     │    «Какой домен → какому сервису?»
│  (nginx pod)    │
└────────┬────────┘
         │ по правилам Ingress
         ▼
┌─────────────────┐
│  Твои приложения│
│  (Pods)         │
└─────────────────┘
```

### 🔍 Простая аналогия: офисное здание

> Представь, что твой кластер — это офис:
> 
> - **LoadBalancer** — это **охрана на входе в здание**. Она знает только: «Пропустить всех на этаж 3, порт 80» и «на этаж 4, порт 443». Она не смотрит, кто именно идёт и зачем.
> - **Ingress Controller** — это **ресепшн на этаже**. Он уже смотрит на бейдж (домен): «А, вы к команде `api.mydomain.com`? Вам направо, в кабинет 305».
> - **Ingress-правила** — это **список на ресепшне**: какой домен → в какой кабинет (сервис) направить.

### 🧩 Почему нельзя обойтись только Ingress Controller?

Потому что **поды (Pods) по умолчанию не имеют внешних IP**. Если ты создашь Deployment с nginx, он будет доступен только *внутри* кластера.

Чтобы добраться до него снаружи, нужен «мост»:

1.  **LoadBalancer-Service** создаёт этот мост на уровне сети: выделяет внешний IP и открывает порты.
2.  **Ingress Controller** (работающий внутри пода) «слушает» эти порты и перенаправляет запросы дальше, согласно правилам.

### 🛠️ Как это выглядит в YAML

```yaml
# 1. LoadBalancer Service — «входная дверь»
apiVersion: v1
kind: Service
metadata:
  name: ingress-nginx-controller
  namespace: ingress-nginx
spec:
  type: LoadBalancer  # ← ServiceLB k3s выдаст внешний IP
  ports:
    - port: 80
      targetPort: 80
    - port: 443
      targetPort: 443
  selector:
    app.kubernetes.io/name: ingress-nginx

# 2. Ingress Resource — «правила маршрутизации»
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-app-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx  # ← какой контроллер обрабатывать
  tls:
  - hosts:
    - "*.mydomain.com"
    secretName: wildcard-tls
  rules:
  - host: api.mydomain.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: my-backend-service
            port:
              number: 8080
```

## 🧠 Коротко для запоминания

| Термин | Уровень | Что делает | Аналогия |
|--------|---------|-----------|----------|
| **LoadBalancer (Service)** | L4 (сеть) | Открывает внешний IP:порт → передаёт трафик в кластер | Охрана на входе в здание |
| **Ingress Controller** | L7 (HTTP) | Читает домен/путь → направляет к нужному сервису | Ресепшн, который распределяет посетителей |
| **Ingress (ресурс)** | Правила | Говорит контроллеру: «домен X → сервис Y» | Список на ресепшне |

## 💡 Практический совет для твоего отчёта

Когда будешь проверять, что Ingress Controller встал:

```bash
kubectl get svc -n ingress-nginx
```

Ты увидишь что-то вроде:
```
NAME                         TYPE           CLUSTER-IP      EXTERNAL-IP     PORT(S)
ingress-nginx-controller     LoadBalancer   10.43.x.x       10.0.2.15       80:32xxx/TCP,443:32xxx/TCP
```

- `EXTERNAL-IP` (`10.0.2.15`) — это тот самый «вход» от ServiceLB.
- Именно на этот IP ты потом направишь свой домен (через DNS или `/etc/hosts` для тестов).

---

Если хочешь, могу показать, как проверить, что трафик действительно проходит цепочку: `твой браузер → LoadBalancer IP → nginx pod → твой сервис`. Это поможет наглядно увидеть разницу уровней для отчёта. 🚀
