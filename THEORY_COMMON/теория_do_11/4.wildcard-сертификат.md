## 🃏 Wildcard-сертификат — простыми словами

**Wildcard-сертификат** (от англ. *wildcard* — «джокер», «универсальная карта») — это **один SSL-сертификат**, который защищает **не один конкретный домен, а сразу все его поддомены первого уровня**.

### 🔑 Ключевой символ: звёздочка `*`

В имени домена звёздочка работает как «заполнитель» (placeholder — место, куда можно подставить любое значение):

```
*.10.174.8.95.nip.io
│
└─ значит: «любой поддомен перед 10.174.8.95.nip.io»
```

### 📋 Что покрывает такой сертификат:

| Запрошенный домен | ✅ Работает с `*.10.174.8.95.nip.io` | Почему |
|-------------------|--------------------------------------|--------|
| `app.10.174.8.95.nip.io` | ✅ Да | Один уровень поддомена |
| `api.10.174.8.95.nip.io` | ✅ Да | Один уровень |
| `grafana.10.174.8.95.nip.io` | ✅ Да | Один уровень |
| `10.174.8.95.nip.io` (без поддомена) | ⚠️ Зависит от настройки | Часто добавляют отдельно в `dnsNames` |
| `dev.api.10.174.8.95.nip.io` | ❌ Нет | Два уровня поддомена — звёздочка не покрывает |

> 💡 **Звёздочка заменяет только одну «часть» домена слева.**  
> `*.example.com` ✅ покрывает `a.example.com`, но ❌ не покрывает `b.a.example.com`.

---

## 🧩 Простая аналогия: пропуск в офис

> Представь, что твой кластер — это **бизнес-центр**:
> 
> - **Обычный сертификат** — это **разовый пропуск** на одно имя: «Иванов, кабинет 305». Только Иванов и только в 305.
> - **Wildcard-сертификат** — это **корпоративный пропуск**: «Сотрудник компании, любой кабинет на 3-м этаже». Один пропуск — доступ ко всем кабинетам этажа (поддоменам).

## 🛡️ Зачем это нужно?

| Проблема без wildcard | Решение с wildcard |
|----------------------|-------------------|
| Для каждого нового сервиса (`api`, `app`, `admin`) нужно выпускать отдельный сертификат | Один сертификат покрывает **все** сервисы сразу |
| Риск забыть продлить сертификат для какого-то поддомена | Продлеваешь один — работают все |
| Сложнее управлять секретами в Kubernetes | Один `Secret` с сертификатом → используют многие Ingress |

## 🔍 Как это выглядит в твоём манифесте

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: wildcard-nipio
spec:
  secretName: wildcard-nipio-tls
  dnsNames:
    - "10.174.8.95.nip.io"      # ← сам домен (без звёздочки)
    - "*.10.174.8.95.nip.io"    # ← wildcard: все поддомены
  issuerRef:
    name: my-ca-issuer
    kind: ClusterIssuer
```

### Что будет внутри сертификата (можно проверить через `openssl`):

```
Subject: CN=10.174.8.95.nip.io
X509v3 Subject Alternative Name:
    DNS:10.174.8.95.nip.io, DNS:*.10.174.8.95.nip.io
Issuer: CN=my-root-ca
```

## 🌐 Как это работает на практике

```
Браузер / curl / Postman
         │
         ▼
Запрос на: https://api.10.174.8.95.nip.io
         │
         ▼
Ingress Controller (nginx) получает запрос
         │
         ▼
Смотрит: «Ага, домен api.10.174.8.95.nip.io»
         │
         ▼
Проверяет сертификат: «*.10.174.8.95.nip.io покрывает api.* — OK ✅»
         │
         ▼
Устанавливает безопасное соединение (HTTPS) и передаёт запрос в нужный сервис
```

## ⚠️ Важные ограничения

1.  **Только один уровень**: `*.example.com` не работает для `a.b.example.com`.
2.  **Только слева**: нельзя написать `api.*.nip.io` — звёздочка всегда заменяет **самую левую** часть.
3.  **Не для всех доменов**: публичные центры (Let's Encrypt) могут блокировать выдачу wildcard для «подозрительных» доменов (как nip.io) — поэтому мы используем локальный CA.
4.  **Приватный ключ**: сертификат бесполезен без приватного ключа — cert-manager хранит их вместе в `Secret` типа `kubernetes.io/tls`.

## 🧰 Как проверить, что сертификат работает

```bash
# 1. Убедиться, что секрет создан:
kubectl get secret wildcard-nipio-tls -n default
# Ожидаем: TYPE = kubernetes.io/tls

# 2. Посмотреть, какие домены покрыты:
kubectl get secret wildcard-nipio-tls -n default -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -text -noout | grep -A1 "Subject Alternative Name"

# 3. Протестировать подключение (флаг -k — игнорировать, что наш CA не в системе доверия):
curl -kv https://app.10.174.8.95.nip.io
# В выводе должно быть: subject: CN=10.174.8.95.nip.io, issuer: CN=my-root-ca
```

## 🧠 Коротко для запоминания

```
🔹 Wildcard = «звёздочка-заполнитель» в домене
🔹 *.example.com покрывает a.example.com, b.example.com, но не a.b.example.com
🔹 Один сертификат → много сервисов → проще управлять
🔹 В Kubernetes хранится в Secret, используется в Ingress через tls.secretName
🔹 Для nip.io выпускаем через локальный CA, потому что Let's Encrypt не доверяет таким доменам
```
