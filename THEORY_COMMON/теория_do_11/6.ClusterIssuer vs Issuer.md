## 🏷️ ClusterIssuer vs Issuer — простыми словами

Оба этих объекта в `cert-manager` — это **издатели сертификатов** (как «паспортные столы»). Но разница — в **масштабе их работы**.

> 🧩 **Аналогия из жизни:**
> 
> | Тип | Аналогия | Где работает |
> |-----|----------|-------------|
> | **Issuer** | Районный паспортный стол | Только в своём районе (неймспейсе) |
> | **ClusterIssuer** | Федеральный паспортный стол (МВД) | Во всей стране (во всём кластере) |

---

## 🔍 Ключевое отличие: область действия (scope)

| Параметр | **Issuer** | **ClusterIssuer** |
|----------|-----------|-----------------|
| **Где работает** | Только в одном `namespace` (например, `default`) | Во **всех** `namespace` кластера |
| **Кто может использовать** | Только приложения в том же неймспейсе | Любое приложение в любом неймспейсе |
| **Уровень доступа** | Локальный | Глобальный (кластерный) |

### Визуально:

```
📦 Кластер Kubernetes
├── 📁 namespace: default
│   ├── 📜 Issuer: local-issuer ✅ (работает только здесь)
│   └── 📜 ClusterIssuer: global-issuer ✅ (работает и здесь)
│
├── 📁 namespace: production
│   ├── 📜 Issuer: local-issuer ❌ (не виден отсюда!)
│   └── 📜 ClusterIssuer: global-issuer ✅ (работает и здесь)
│
└── 📁 namespace: monitoring
    └── 📜 ClusterIssuer: global-issuer ✅ (тоже работает)
```

## 📝 Примеры в YAML

### 🔹 Issuer (локальный, только для своего неймспейса)

```yaml
apiVersion: cert-manager.io/v1
kind: Issuer  # ← обрати внимание: Issuer, не ClusterIssuer
metadata:
  name: local-issuer
  namespace: default  # ← работает ТОЛЬКО в default
spec:
  ca:
    secretName: my-ca-secret
```

**Кто может его использовать:**
```yaml
# ✅ Работает: сертификат в том же неймспейсе (default)
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: my-cert
  namespace: default  # ← тот же неймспейс, что и Issuer
spec:
  issuerRef:
    name: local-issuer  # ← найдёт его
    kind: Issuer
```

```yaml
# ❌ НЕ сработает: сертификат в другом неймспейсе
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: my-cert
  namespace: production  # ← другой неймспейс!
spec:
  issuerRef:
    name: local-issuer  # ← ошибка: Issuer не виден из production
    kind: Issuer
```

---

### 🔹 ClusterIssuer (глобальный, для всего кластера)

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer  # ← кластерный уровень!
metadata:
  name: global-issuer  # ← namespace НЕ указывается (он кластерный)
spec:
  ca:
    secretName: my-ca-secret
```

**Кто может его использовать:**
```yaml
# ✅ Работает в default:
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: cert-1
  namespace: default
spec:
  issuerRef:
    name: global-issuer
    kind: ClusterIssuer  # ← указываем правильный тип!

# ✅ Работает в production:
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: cert-2
  namespace: production
spec:
  issuerRef:
    name: global-issuer
    kind: ClusterIssuer

# ✅ Работает в monitoring:
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: cert-3
  namespace: monitoring
spec:
  issuerRef:
    name: global-issuer
    kind: ClusterIssuer
```

## 🎯 Когда что использовать?

| Ситуация | Что выбрать | Почему |
|----------|------------|--------|
| 🔹 Учебный проект, один неймспейс | Можно `Issuer` | Проще, меньше прав |
| 🔹 Реальный кластер, много сервисов в разных неймспейсах | **`ClusterIssuer`** | Один издатель — все сервисы |
| 🔹 Изолированный проект с отдельным CA | `Issuer` | Безопаснее: другие неймспейсы не получат доступ |
| 🔹 Корпоративный корневой CA для всей компании | **`ClusterIssuer`** | Стандартный паттерн: один корень — всё дерево |

> 💡 **В твоём проекте (Школа 21, Advanced Kubernetes)**:  
> Мы используем **`ClusterIssuer`**, потому что:
> 1. Задание требует, чтобы `cert-manager` мог выпускать сертификаты для любого Ingress в кластере
> 2. Это имитирует реальную практику: корпоративный CA доступен всем командам
> 3. Проще управлять: один издатель, а не по одному на каждый неймспейс

## 🔐 Важный нюанс: где хранится секрет с ключом?

Независимо от типа издателя, **приватный ключ и сертификат CA хранятся в `Secret`**, и этот `Secret` должен быть в том же неймспейсе, где его ищет издатель.

```yaml
# Для ClusterIssuer:
# Secret должен быть в том неймспейсе, где работает cert-manager (обычно cert-manager)
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: my-ca-issuer
spec:
  ca:
    secretName: my-root-ca-secret  # ← ищет в неймспейсе сертификата!
```

```yaml
# Для Issuer:
# Secret должен быть в том же неймспейсе, что и сам Issuer
apiVersion: cert-manager.io/v1
kind: Issuer
metadata:
  name: local-issuer
  namespace: default
spec:
  ca:
    secretName: my-local-secret  # ← ищет в default
```

> ⚠️ **Частая ошибка:** создать `ClusterIssuer`, который ссылается на `Secret` в `default`, а сам `Secret` лежит в `cert-manager`. cert-manager не найдёт его → сертификат не выпустится.

## 🧠 Коротко для запоминания

```
🔹 Issuer = локальный издатель (работает в одном неймспейсе)
🔹 ClusterIssuer = глобальный издатель (работает во всём кластере)
🔹 В YAML: kind: Issuer или kind: ClusterIssuer
🔹 В issuerRef: обязательно указывать правильный kind!
🔹 Secret с ключом должен быть там, где его ищет издатель
🔹 В учебных и корпоративных проектах чаще используют ClusterIssuer
```

### Почему ClusterIssuer, а не Issuer?

В проекте использован `ClusterIssuer`, так как:
- Требуется возможность выпускать сертификаты для Ingress 
  в любом неймспейсе кластера
- Это соответствует реальной практике: корневой CA организации 
  доступен всем командам и сервисам
- Упрощает управление: один издатель вместо множества локальных

Пример ссылки из Certificate:
```yaml
issuerRef:
  name: my-ca-issuer
  kind: ClusterIssuer  # ← явно указываем тип
```

## 🛠️ Быстрая проверка: какой издатель где виден

```bash
# Посмотреть все ClusterIssuer (кластерный уровень):
kubectl get clusterissuer

# Посмотреть Issuer только в текущем неймспейсе:
kubectl get issuer

# Посмотреть Issuer во всех неймспейсах:
kubectl get issuer -A

# Проверить, может ли сертификат в неймспейсе 'production' 
# использовать издатель 'local-issuer' из 'default':
kubectl describe certificate my-cert -n production
# Если ошибка "Issuer not found" — значит, scope не совпадает
```
