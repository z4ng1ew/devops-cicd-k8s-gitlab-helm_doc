## Замечание 1: «Почему Nginx Ingress, а не API Gateway?»

Это **критичный момент** — давай сразу разберёмся, кто прав:

То есть ревьюер **прав по факту**. Но он говорит «не получает обновления и патчи безопасности» — это **не совсем точно**, проект пока **ещё** получает критические патчи (последний релиз был в апреле 2025 после IngressNightmare).

## Замечание 4: «Сертификат можно было создать через аннотацию Ingress»

### Кто прав

**Ревьюер прав в плане элегантности**, но **ты прав по букве задания**.

В Ingress можно написать:
```yaml
metadata:
  annotations:
    cert-manager.io/cluster-issuer: my-ca-issuer
spec:
  tls:
    - hosts: [gateway.example.com]
      secretName: gateway-tls
```

И cert-manager автоматически создаст `Certificate` под капотом + выпустит сертификат + положит в `Secret` `gateway-tls`. Это называется **ingress-shim** (тонкая прослойка между Ingress и cert-manager).

**НО** — этот авто-созданный Certificate **не будет wildcard**. Он будет валиден только для тех hosts, которые перечислены в `spec.tls.hosts`. Если у тебя там `gateway.example.com` — сертификат будет именно на это имя, без `*`.

### Что нужно было ответить

```

   Ingress-shim создаёт сертификат только под перечисленные hosts. 
   Если бы я положился на shim, я бы получил сертификат на 
   "gateway.10.174.8.95.nip.io" — это НЕ wildcard.

2. Один wildcard на весь домен — это правильная практика для группы 
   связанных сервисов: один Secret переиспользуется в разных Ingress-

правильный путь под формулировку задания.
```

## Замечание 5: «PostgreSQL и RabbitMQ — лучше StatefulSet, а не Deployment»

### Кто прав

**Ревьюер прав на 100%.** Это **главное** замечание в его защите и самое важное для тебя как обучения.

### Почему StatefulSet, а не Deployment

| Что | Deployment | StatefulSet |
|---|---|---|
| **Имена подов** | Случайные (`postgres-7f8c9-abcde`) | Предсказуемые (`postgres-0`, `postgres-1`) |
| **Порядок старта** | Все одновременно | По порядку: `-0` → `-1` → `-2` |
| **Порядок остановки** | Любой | Обратный: `-2` → `-1` → `-0` |
| **PVC на под** | Все поды делят один PVC | Каждому поду — свой PVC |
| **Сетевая идентификация** | Service балансит по любому | Каждый под имеет **stable DNS**: `postgres-0.postgres-headless.default.svc` |
| **Кейс** | Stateless web-серверы | Базы, очереди, кластеры с состоянием |

### Конкретно для нашего случая

**У тебя репликов = 1**, и формально для одного реплика разница между Deployment и StatefulSet **минимальна**. Поэтому твой сетап **работает**. Но если завтра ты захочешь:
- Поднять PostgreSQL Primary + 2 Replicas — Deployment **не справится** (каждой реплике нужен свой том + порядок старта)
- Поднять RabbitMQ-кластер из 3 нод — Deployment **не справится** (кластер требует stable hostnames)

### Почему «мы так не сделали» в нашем сетапе

Признаюсь — это **моя недоработка**, я не стал переделывать архитектуру DO10. Для нашей задачи (одна реплика, демо) **Deployment + PVC работает корректно**, что доказывают прошедшие Postman-тесты. Но **правильно** было бы:

```yaml
# Правильный вариант
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres-headless   # обязательно headless Service
  replicas: 1
  selector:
    matchLabels:
      app: postgres
  template:
    # ... как в Deployment
  volumeClaimTemplates:             # ВМЕСТО отдельного PVC!
    - metadata:
        name: postgres-storage
      spec:
        accessModes: [ReadWriteOnce]
        storageClassName: manual
        resources:
          requests:
            storage: 5Gi
```

`volumeClaimTemplates` — это **главное отличие**. StatefulSet сам создаёт PVC для каждого пода по шаблону.

### Что доучить (это серьёзно)

- **StatefulSet vs Deployment** — обязательно для DevOps уровня middle
- **Headless Service** — Service без ClusterIP, нужен для StatefulSet
- **volumeClaimTemplates** — автогенерация PVC по шаблону
- **PodDisruptionBudget** для stateful workloads
- **Pod Topology Spread Constraints** — где правильно располагать поды
- **Operators**: PostgreSQL Operator (Zalando, Crunchy), RabbitMQ Operator — в production даже StatefulSet не пишут руками, а используют операторы

**Оценка вопроса: 10/10** — это **самое сильное** и **самое полезное** для тебя замечание.
