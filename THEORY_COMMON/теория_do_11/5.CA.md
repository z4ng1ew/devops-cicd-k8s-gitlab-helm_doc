## 🏛️ CA (Certificate Authority) — простыми словами

**CA** (Certificate Authority / Удостоверяющий центр) — это **организация или сервис, который выдаёт и подписывает цифровые сертификаты**. Это как «паспортный стол» или «нотариус» в мире интернета.

> 🧩 **Аналогия из жизни:**
> 
> | Реальный мир | Мир сертификатов |
> |-------------|-----------------|
> | Паспортный стол (МВД) | **CA** (Certificate Authority) |
> | Паспорт с печатью | **Сертификат** с цифровой подписью |
> | Печать и подпись сотрудника МВД | **Цифровая подпись** центра |
> | Ты доверяешь паспорту, потому что доверяешь МВД | Браузер доверяет сайту, потому что доверяет CA |

---

## 🔐 Что именно делает CA?

1.  **Проверяет**, что тот, кто просит сертификат, действительно владеет доменом (или организацией).
2.  **Подписывает** сертификат своим приватным ключом — это как поставить печать и подпись на паспорте.
3.  **Гарантирует** всем остальным: «Да, этому сайту можно доверять, я проверил».

---

## 🌐 Примеры известных публичных CA

| Название | Для чего используется |
|----------|----------------------|
| **Let's Encrypt** | Бесплатные сертификаты для сайтов (самый популярный) |
| **DigiCert** | Платные сертификаты для бизнеса, банков |
| **GlobalSign** | Корпоративные и государственные решения |
| **Sectigo** | Широкий спектр сертификатов |

Браузеры (Chrome, Firefox) и операционные системы **уже имеют список доверенных CA**. Если сертификат подписан одним из них — браузер молча показывает «замочек» 🔒. Если нет — показывает предупреждение 🚫.

## ❓ Почему в твоём проекте мы создаём СВОЙ локальный CA?

Потому что:

| Проблема | Решение |
|----------|---------|
| 🔹 **nip.io** — публичный сервис, но **Let's Encrypt не выдаёт** на него сертификаты (защита от злоупотреблений) | Создаём **свой CA внутри кластера** через `cert-manager` |
| 🔹 Нам нужен **wildcard** (`*.10.174.8.95.nip.io`) для удобства | Наш локальный CA может подписать что угодно — мы же им управляем |
| 🔹 Это **учебный проект**, не для реального интернета | Самоподписанный корневой сертификат — нормально для тестов |

> 💡 **На работе в банке** ты наверняка видел внутренние сертификаты, подписанные корпоративным CA (например, «РСХБ-Root-CA»). Принцип тот же: компания сама себе «паспортный стол».

## 🔄 Цепочка доверия (как это работает)

```
🌍 Публичный интернет:
Браузер доверяет → Публичному CA (Let's Encrypt) → который подписал сертификат твоего сайта

🏢 Твой локальный кластер:
Ты (админ) доверяешь → Своему CA (my-root-ca) → который подписал wildcard-сертификат
```

### Как это выглядит в твоём проекте:

```yaml
# 1. Самоподписанный "бутстрап" (временный, только чтобы создать корень)
ClusterIssuer: selfsigned-bootstrap
     │
     ▼ подписывает
# 2. Наш корневой сертификат (главный "паспортный стол")
Certificate: my-root-ca (isCA: true)
     │
     ▼ используется как основа для
# 3. Настоящий издатель
ClusterIssuer: my-ca-issuer
     │
     ▼ подписывает
# 4. Wildcard-сертификат для твоих сервисов
Certificate: wildcard-nipio (*.10.174.8.95.nip.io)
```

## 🧱 Из чего состоит CA технически?

Удостоверяющий центр — это **пара ключей + сертификат**:

| Компонент | Что это | Где хранится в твоём проекте |
|-----------|---------|-----------------------------|
| **Приватный ключ** (Private Key) | Секретный ключ для подписи | В `Secret: my-root-ca-secret` (никому не показывать!) |
| **Публичный ключ** (Public Key) | Открытая часть, встроена в сертификат | Внутри сертификата `my-root-ca` |
| **Сертификат** (X.509) | Сам «паспорт» центра: кто он, срок действия | В том же `Secret`, поле `ca.crt` |

> ⚠️ **Важно:** Если приватный ключ твоего локального CA утечёт — злоумышленник сможет подписывать поддельные сертификаты от имени твоего центра. Поэтому в `Secret` и есть защита.

## 🛠️ Как браузер/клиент узнаёт, что доверять твоему локальному CA?

По умолчанию — **никак**. Поэтому есть два пути:

| Способ | Как работает | Для чего подходит |
|--------|-------------|------------------|
| 🔹 **Флаг `-k` в curl** | Игнорировать проверку сертификата | Быстрые тесты, не для продакшена |
| 🔹 **Добавить CA в доверенные** | Скопировать `ca.crt` в хранилище доверенных сертификатов ОС | Локальная разработка, демо, внутренние системы |

### Пример для Ubuntu (твой случай):

```bash
# 1. Достать корневой сертификат из секрета
kubectl get secret my-root-ca-secret -n cert-manager -o jsonpath='{.data.ca\.crt}' | base64 -d > my-root-ca.crt

# 2. Добавить в доверенные
sudo cp my-root-ca.crt /usr/local/share/ca-certificates/
sudo update-ca-certificates

# 3. Теперь curl и браузер будут доверять сертификатам, подписанным этим CA
curl https://app.10.174.8.95.nip.io  # без флага -k!
```

## 🧠 Коротко для запоминания

```
🔹 CA = Certificate Authority = Удостоверяющий центр = «паспортный стол для сайтов»
🔹 Выдаёт и подписывает сертификаты, ставит «цифровую печать»
🔹 Браузеры доверяют только сертификатам от известных публичных CA
🔹 В локальных/корпоративных средах создают свой CA — как в твоём проекте
🔹 В Kubernetes CA хранится в Secret, используется cert-manager для выпуска других сертификатов
```

## 💡 Совет для отчёта

В `REPORT.MD` можно кратко пояснить:

```markdown
### Локальный удостоверяющий центр (CA)

Поскольку публичные центры (Let's Encrypt) не выдают сертификаты 
на домены вида `*.nip.io`, в кластере развёрнут локальный CA 
через cert-manager:

1. Самоподписанный bootstrap-issuer создал корневой сертификат `my-root-ca`
2. На его основе создан ClusterIssuer `my-ca-issuer`
3. Этот издатель подписал wildcard-сертификат для `*.10.174.8.95.nip.io`

Для локальных тестов корневой сертификат можно добавить в доверенные 
на хост-машине: `sudo update-ca-certificates`.
```
