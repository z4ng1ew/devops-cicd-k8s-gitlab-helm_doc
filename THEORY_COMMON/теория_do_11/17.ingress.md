## 🚦 Ingress Controller — простыми словами

**Ingress Controller** (Ингресс-контроллер) — это **«умный шлюз»**, программа, которая стоит на входе в твой кластер Kubernetes и **решает, куда направить каждый входящий запрос** (из браузера, Postman, мобильного приложения).

> 🧩 **Аналогия из жизни:**
> 
> Представь, что твой кластер — это **большой бизнес-центр**:
> 
> | Реальный мир | Мир Kubernetes |
> |-------------|---------------|
> | 🏢 Бизнес-центр с 100 офисами | Кластер с 50+ сервисами (подами) |
> | 🚪 Охрана на входе + ресепшн | **Ingress Controller** |
> | 📋 Список: «Компания А → этаж 3, офис 305» | **Ingress-правила** (YAML-манифест) |
> | 🧑 Посетитель с пропуском | HTTP/HTTPS-запрос от пользователя |
> 
> **Ingress Controller** — это охрана + ресепшн в одном лице: он смотрит на «пропуск» (домен/путь) и говорит: «Вам направо, в сервис `session-service`».

---

## 🔍 Ingress vs Ingress Controller — в чём разница?

Это два разных объекта, которые часто путают:

| Объект | Что это | Кто создаёт | Аналогия |
|--------|---------|------------|----------|
| **Ingress** (ресурс) | 📄 **Правила маршрутизации** в YAML: «домен `api.example.com` → сервис `my-app:8080`» | Ты (разработчик) | 📋 Список на ресепшне: «Иванов → кабинет 305» |
| **Ingress Controller** | ⚙️ **Программа**, которая читает эти правила и реально пересылает трафик | Админ кластера (ты ставишь его один раз) | 👮 Охранник + ресепшионист, который работает по списку |

### 🔄 Как они работают вместе:

```
1. Ты создаёшь Ingress (YAML-файл):
   └─ "Запросы на /api/v1/auth → отправляй на session-service:8081"

2. Ingress Controller (Nginx) видит новый Ingress:
   └─ "О, новое правило! Записал в свою конфигурацию"

3. Пользователь стучится:
   └─ GET https://app.10.174.8.95.nip.io/api/v1/auth/authorize

4. Controller смотрит на запрос:
   └─ Домен: app.10.174.8.95.nip.io ✅
   └─ Путь: /api/v1/auth/* ✅
   └─ Правило: → session-service:8081

5. Controller пересылает запрос внутрь кластера:
   └─ session-service получает запрос → обрабатывает → возвращает ответ
```

## 🛠️ Какой Ingress Controller используешь ты?

В твоём проекте (DO11, k3s):

| Компонент | Значение |
|-----------|----------|
| **Тип** | Nginx Ingress Controller (официальный от Kubernetes) |
| **Где работает** | В поде `ingress-nginx-controller` в неймспейсе `ingress-nginx` |
| **Как попал в кластер** | Ты применил манифест: `kubectl apply -f https://raw.githubusercontent.com/.../deploy.yaml` |
| **Как принимает трафик** | Через Service типа `LoadBalancer` → k3s ServiceLB выдал внешний IP (`10.174.8.91`) |
| **Что слушает** | Порты 80 (HTTP) и 443 (HTTPS) |

```
Твой браузер / Postman
         │
         ▼

         │
         ▼
[Internet] → [k3s-кластер]
                    │

         ┌─────────────────────┐

                  │ порт 443 (HTTPS)
                  ▼
         ┌─────────────────────┐
         │ Ingress Controller  │ ← "умный маршрутизатор"
         │ (Nginx в поде)      │
         └────────┬────────────┘
                  │ смотрит на:
                  │ • домен: app.10.174.8.95.nip.io
                  │ • путь: /api/v1/auth
                  ▼
         ┌─────────────────────┐
         │ Ingress-правило     │ ← твой YAML-манифест
         │ /api/v1/auth/* →    │
         │ session-service:8081│
         └────────┬────────────┘
                  ▼
         ┌─────────────────────┐
         │ session-service     │ ← твой Java-микросервис
         │ (под с приложением) │
         └─────────────────────┘
```

## 📝 Пример: как выглядит Ingress в YAML

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx  # ← какой Controller обрабатывать (наш Nginx)
  tls:
  - hosts:
    - "app.10.174.8.95.nip.io"
    secretName: wildcard-nipio-tls  # ← наш сертификат
  rules:
  - host: "app.10.174.8.95.nip.io"
    http:
      paths:
      # 🔹 Auth-запросы → session-service
      - path: /api/v1/auth
        pathType: Prefix
        backend:
          service:
            name: session-service
            port:
              number: 8081
      # 🔹 Gateway-запросы → gateway-service
      - path: /api/v1/gateway
        pathType: Prefix
        backend:
          service:
            name: gateway-service
            port:
              number: 8087
```

## ❓ Почему нельзя обойтись без Ingress Controller?

| Без Ingress Controller | С Ingress Controller |
|----------------------|---------------------|
| 🔹 Каждый сервис нужен свой внешний IP/порт | 🔹 Один IP (LoadBalancer) на весь кластер |
| 🔹 Нет HTTPS «из коробки» | 🔹 Автоматическое TLS-шифрование (через cert-manager) |
| 🔹 Сложно менять маршруты (надо пересоздавать Service) | 🔹 Правила в YAML: изменил → применил → работает |
| 🔹 Нет единой точки для логирования, аутентификации, лимитов | 🔹 Можно добавить middleware: rate limiting, CORS, auth |

> 💡 **Ingress Controller — это стандартный способ** дать внешнему миру доступ к внутренним сервисам Kubernetes. Без него тебе пришлось бы открывать каждый сервис через `NodePort` или `LoadBalancer` отдельно — это неудобно и небезопасно.

## ❓ Частые вопросы

**В: А если Ingress Controller упадёт?**  
О: Если под `ingress-nginx-controller` перезапустится — трафик временно не будет проходить. Поэтому в продакшене его запускают с `replicas: 2+` и `podAntiAffinity`, чтобы он был отказоустойчивым.

**В: Можно ли использовать другой Controller, не Nginx?**  
О: Да! Популярные альтернативы: Traefik (стоит в k3s по умолчанию), HAProxy, Contour. Но Nginx — самый распространённый и документированный.

**В: Почему в k3s по умолчанию Traefik, а мы ставим Nginx?**  
О: Потому что в задании прямо сказано: «Установить Ingress Controller Nginx вместо стандартного». Это учебная цель — научиться ставить и настраивать контроллер вручную.
