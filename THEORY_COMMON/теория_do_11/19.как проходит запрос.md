# Это золотой вопрос — на нём «плавают» 80% кандидатов на DevOps

Дам тебе **полный путь пакета**, от твоего ноутбука до пода с приложением. Каждый этап важен, и на каждом есть «заковырки», на которых сыпется большинство. Это **сценарий ответа на собеседовании или peer-review**, не теория — а именно про нашу архитектуру DO11.

---

# Сценарий: пользователь делает `curl https://gateway.10.174.8.95.nip.io/api/v1/gateway/hotels`

Что происходит **по шагам**.

## Этап 0. DNS-резолвинг

Браузер/curl сначала спрашивает у системы: «какой IP у `gateway.10.174.8.95.nip.io`?»

ОС идёт в **systemd-resolved** (или другой DNS-резолвер), тот спрашивает у DNS-серверов в `/etc/resolv.conf` (обычно DNS провайдера или Cloudflare 1.1.1.1).

Сервер **nip.io** — это публичный wildcard-DNS, который для любого имени `<IP>.nip.io` возвращает тот самый IP. Здесь — `10.174.8.95`.

🎯 **Заковырка**: nip.io работает только потому, что у него настроена wildcard-запись в DNS-зоне. Если бы интернета не было — резолвинг сломался бы. В корпоративных сетях с фильтрами nip.io тоже могут заблокировать как «подозрительный wildcard-домен». Альтернатива: прописать `127.0.0.1 my.local` в `/etc/hosts` локально.

## Этап 1. TCP-соединение и TLS-handshake

Пакет идёт на `10.174.8.95:443`. Это **IP мастер-ноды k3s**. Multipass выдал этот IP виртуальной машине через свой NAT-мост.

На порту 443 слушает **Nginx Ingress Controller**. Точнее, не он сам, а **kube-proxy** на ноде перенаправляет пакет на порт пода Nginx через iptables/IPVS-правила (об этом дальше).

Nginx видит входящее соединение → начинается **TLS-handshake** (рукопожатие):

1. Клиент шлёт `ClientHello` + **SNI** (Server Name Indication — расширение TLS, где клиент в открытом виде сообщает, какой именно домен ему нужен; нужно, потому что один IP может обслуживать много доменов).
2. Сервер по SNI находит подходящий сертификат. У нас Nginx Ingress смотрит на список своих Ingress-ресурсов: для `gateway.10.174.8.95.nip.io` в Ingress `app-ingress` указано `secretName: wildcard-nipio-tls` → Nginx берёт этот сертификат из Secret и отдаёт.
3. Клиент проверяет цепочку сертификата. Сертификат подписан нашим `my-root-ca`, которого нет в системном trust store браузера → пишет «Не защищено» / `curl` ругается без `-k`.
4. Если клиент всё-таки соглашается → согласуется симметричный ключ, дальше канал зашифрован.

🎯 **Заковырки**:
- **SNI обязателен**: без него Nginx не понимает, какой сертификат отдать, и вернёт сертификат по умолчанию (часто self-signed).
- **HTTP-01 challenge для Let's Encrypt** работает ровно потому, что использует SNI: ACME-сервер стучится на 80 порт по имени домена, и Nginx по SNI понимает, какому Ingress отдать challenge-файл.
- **Самоподписанный CA** в production — табу. У нас — учебная задача, поэтому такой подход допустим.

## Этап 2. От Nginx Ingress Controller до пода

Теперь HTTPS-трафик внутри Nginx. Что он делает:

1. Парсит HTTP-заголовок `Host: gateway.10.174.8.95.nip.io`.
2. Смотрит в свой `nginx.conf` (он автогенерируется из Ingress-ресурсов k8s каждые ~10 секунд).
3. Находит `server { server_name gateway.10.174.8.95.nip.io; ... }` с `location / { proxy_pass http://upstream-gateway; }`.
4. Здесь `upstream-gateway` — это **не Service**, а **прямой список IP-адресов подов** gateway-service! Nginx Ingress в k3s/k8s **обходит Service** для performance: он подписан на API Kubernetes и сам получает список эндпоинтов через **EndpointSlices**.

🎯 **Главная заковырка для собеседования**: «А Service же балансирует трафик через iptables — почему Nginx его обходит?»

Ответ: для performance и для использования собственного алгоритма балансировки (round-robin, least-conn, EWMA — exponentially weighted moving average). Service делает балансировку через `iptables -m statistic --mode random --probability` — это **случайный выбор**, не настоящий round-robin. Nginx делает «честнее». Плюс при обходе Service у него меньше hops (переходов через сетевой стек).

## Этап 3. Service и kube-proxy

Это самый каверзный для интервью этап. **Если бы** Nginx ходил через Service (а другие сервисы внутри кластера именно так и ходят), то:

1. У Service `gateway-service` есть **ClusterIP** — фиктивный IP из подсети `10.43.0.0/16` (по умолчанию у k3s).
2. Этот IP **не принадлежит никакой сетевой карте** — он существует только в правилах iptables.
3. При запросе на `gateway-service:8087` ОС резолвит имя в ClusterIP через **CoreDNS** (под `coredns` в `kube-system`).
4. Пакет на `10.43.X.X:8087` попадает в **kube-proxy**, который через iptables (или IPVS, если включён) перенаправляет его на IP конкретного пода — например, `10.42.1.5:8087`.
5. Это работает через **DNAT** (Destination Network Address Translation — подмена destination-IP в пакете).

🎯 **Заковырка**: «А почему ClusterIP, который ни к чему не привязан, всё-таки работает?»

Ответ: потому что **iptables** в режиме `nat` перехватывает пакеты ещё в ядре, на этапе `PREROUTING` или `OUTPUT`. Когда ядро видит destination = ClusterIP, правило срабатывает раньше, чем ядро попытается отправить пакет наружу. Это вся магия Service.

🎯 **Заковырка №2**: «А что если под умрёт?»

Ответ: **endpoint controller** (часть kube-controller-manager) постоянно следит за подами, которые матчатся под `selector` Service. Когда под умирает — он удаляется из EndpointSlice → kube-proxy обновляет iptables → пакеты перестают идти к мёртвому поду. Лаг — обычно 1-2 секунды.

## Этап 4. Pod → контейнер → приложение

Пакет долетел до пода `gateway-service-xxx` на IP `10.42.1.5:8087`.

1. **CNI plugin** (Container Network Interface — стандарт сетевого взаимодействия в k8s; в k3s по умолчанию используется **Flannel**) обеспечивает доступность пода. Каждая нода получает свою подсеть подов (например, `k3s-master` = `10.42.0.0/24`, `k3s-worker1` = `10.42.1.0/24`).
2. На ноде есть **bridge interface** (мост, как в обычном Linux-bridge), к которому подключены все veth-устройства подов.
3. Внутри пода — Linux network namespace со своим eth0 (на самом деле veth-парой).
4. Пакет долетает до контейнера, нашего Java-приложения. **Spring Boot** обрабатывает запрос.

🎯 **Заковырка**: «А как пакет с одной ноды попадает на другую, если поды на разных нодах?»

Ответ: через **VXLAN-туннель** (Virtual Extensible LAN — оверлейная сеть). Flannel оборачивает (encapsulate) пакеты пода в UDP-пакеты и шлёт их между нодами по «настоящей» сети. Принимающий Flannel разворачивает (decapsulate). Это и есть «overlay network» (наложенная сеть).

## Этап 5. Внутри пода — Spring Boot + JWT

Gateway-service получил запрос. Что он делает:

1. **JWT-фильтр** проверяет заголовок `Authorization: Bearer ...`. Если токен валидный (подпись совпадает с открытым ключом из конфига) и не истёк (поле `exp`) — пропускает дальше.
2. Контроллер `GatewayController` понимает, что нужен endpoint `/api/v1/gateway/hotels`. Делегирует на `HotelsServiceImplementation`.
3. Тот делает HTTP-запрос на `http://hotel-service:8082/...` (имя из ConfigMap).
4. CoreDNS резолвит `hotel-service` в ClusterIP → kube-proxy → pod hotel-service → JPA (Java Persistence API — стандарт работы с БД в Java) → запрос в `postgres:5432` → 6 БД, выбирается `hotels_db` → SELECT → JSON-ответ.

## Этап 6. Обратный путь

Ответ идёт ровно тем же путём, но в обратную сторону:

`hotel-service pod` → `postgres pod` (для запроса в БД) → `hotel-service` → `gateway pod` → Nginx Ingress (видит response из upstream) → TLS-encryption → твой curl.

🎯 **Заковырка**: «А как Nginx знает, что ответ пришёл именно от того пода, к которому он шёл?»

Ответ: TCP-сессия. Nginx держит открытый TCP-сокет к конкретному поду, ответ приходит по тому же сокету. На уровне TCP это **stateful** взаимодействие.

# Краткая «шпаргалка для проверки»

Если на peer-review спросят «расскажи, как идёт запрос», отвечай **тремя слоями**:

## Слой 1 — внешний (L4/L7)

`Client → DNS (nip.io) → IP мастера (10.174.8.95:443) → Nginx Ingress (TLS-termination, проверка SNI, маршрутизация по Host-заголовку)`

## Слой 2 — Kubernetes-сеть

`Nginx Ingress → EndpointSlice (минуя Service, прямо к подам) → CNI Flannel → Pod IP`

или, для **межсервисного** взаимодействия внутри кластера:

`Service (ClusterIP) → CoreDNS → iptables/kube-proxy → DNAT → Pod`

## Слой 3 — внутри пода

`Контейнер → JWT-проверка → Spring контроллер → HTTP в соседний Service → CoreDNS → ... → PostgreSQL → JPA → JSON-ответ`

# Самые частые «коварные» вопросы

**В: А зачем вообще ClusterIP, если можно ходить напрямую на под?**

О: Под может умереть и пересоздаться с **новым** IP. ClusterIP стабилен — он живёт, пока живёт Service. Это **уровень абстракции от реальной сети к логическим именам**.

**В: А что будет, если ноду выключить?**

О: 
1. Через несколько секунд kubelet перестаёт слать healthcheck в API-сервер.
2. Через ~30 секунд (taint-based-eviction timeout) controller-manager помечает ноду `NotReady`.
3. Поды на этой ноде помечаются для пересоздания на других нодах.
4. EndpointSlice обновляется → kube-proxy убирает старые правила → трафик перестаёт идти к мёртвым подам.

У нас БД лежит **только на master** (через nodeAffinity + PV типа hostPath), так что выключение master = смерть БД. Это **известный минус** нашего сетапа, в production используют облачные PV или distributed storage (Ceph, Longhorn).

**В: А почему вы решили использовать Ingress, а не NodePort, как было в DO10?**

О: NodePort открывает порт на **каждой ноде**, его номер случайный (30000-32767). Это (а) криво для домена, (б) увеличивает поверхность атаки (attack surface — всё, через что можно атаковать систему), (в) не поддерживает TLS-termination без танцев. Ingress даёт: один входной IP, один сертификат на wildcard, понятная маршрутизация по хостам и путям.

**В: Зачем в кластере собственный CA, если есть Let's Encrypt?**

О: Let's Encrypt не выдаёт сертификаты на nip.io (они блокируют wildcard-сервисы для предотвращения abuse). В production используют:
- DNS-01 challenge с реальным доменом → wildcard от Let's Encrypt
- Внутренний CA для внутренних сервисов (типичный enterprise-сетап — РСХБ тоже использует свой CA для внутренних API)

**В: Почему в `imagePullPolicy: Never`?**

О: Образы предзагружены в containerd на каждой ноде через `k3s ctr images import`. Если поставить `IfNotPresent` или `Always`, k3s будет пытаться сходить в Docker Hub за обновлением → таймаут, ImagePullBackOff. `Never` гарантирует: использовать только то, что уже есть локально. **В production делается наоборот**: образы кладутся в private registry, k3s имеет credentials для доступа, и `imagePullPolicy: IfNotPresent`.

**В: А что произойдёт с трафиком, если Nginx Ingress упадёт?**

О: У нас 1 реплика контроллера → секунд 30-60 будет downtime, пока он не перезапустится. В production делают **2-3 реплики Nginx Ingress** + **ExternalIP с балансировкой** (MetalLB, или облачный LB). У нас же ServiceLB k3s балансирует трафик между нодами, но если упадёт **под** Ingress (а не нода), пока он не поднимется — трафик никуда не идёт.
