## 🚪 Gateway Service vs Ingress Controller — в чём разница?

Отличный вопрос! На первый взгляд они действительно делают похожее — **принимают внешние запросы**. Но они работают на **разных уровнях** и решают **разные задачи**.

> 🧩 **Аналогия из жизни: доставка пиццы**
>
> | Компонент | Аналогия | Что делает |
> |-----------|----------|-----------|
> | **Ingress Controller** | 🏢 **Шлагбаум на въезде в ЖК** | Пропускает машины на территорию, говорит: «Вам в дом №5» |
> | **Gateway Service** | 🚪 **Консьерж в подъезде №5** | Принимает заказ, проверяет паспорт, передаёт курьеру на этаж |
> | **Микросервисы** | 🍕 **Кухня, касса, курьеры внутри** | Готовят пиццу, принимают оплату, доставляют |

---

## 🔍 Ключевые отличия (таблица)

| Критерий | **Ingress Controller** | **Gateway Service** (твой `gateway-service`) |
|----------|----------------------|---------------------------------------------|
| **Уровень** | 🌐 **Инфраструктурный** (часть Kubernetes) | 🧩 **Прикладной** (часть твоего приложения) |
| **Что это** | ⚙️ Программа (Nginx, Traefik) | 💻 Твой Java-код (Spring Boot) |
| **Где работает** | В поде `ingress-nginx-controller` | В поде `gateway-service` |
| **На что смотрит** | Домен, путь, порт (`/api/v1/auth`) | Бизнес-логика, токены, валидация данных |
| **Зачем нужен** | Маршрутизация трафика **между сервисами** | Маршрутизация запросов **внутри бизнес-домена** |
| **Кто настраивает** | DevOps / админ кластера | Разработчик приложения |
| **Масштабируется** | Репликами пода (как любой Deployment) | Репликами пода + балансировкой внутри приложения |

## 🎯 Зачем вообще нужен Gateway Service, если есть Ingress?

Потому что **они решают разные проблемы**:

### 🔹 Ingress Controller решает **инфраструктурные** задачи:
| Задача | Пример |
|--------|--------|
| 🌐 Единая точка входа | Один внешний IP на 50 сервисов |
| 🔐 Терминация TLS | HTTPS → HTTP внутри кластера |
| 🗂️ Базовая маршрутизация | `/api/*` → сервис А, `/admin/*` → сервис Б |
| 📊 Логирование доступа | Кто, когда, куда стучался |
| 🚫 Блокировка по IP | Rate limiting, blacklist |

### 🔹 Gateway Service решает **бизнес-задачи**:
| Задача | Пример |
|--------|--------|
| 🔑 Аутентификация | Проверка JWT-токена, роли пользователя |
| 🧩 Агрегация данных | Запросить `hotel-service` + `loyalty-service` → вернуть один ответ |
| 🔄 Трансформация | Преобразовать формат ответа для мобильного приложения |
| 🛡️ Валидация | Проверить, что `hotelId` — UUID, а не мусор |
| 📦 Кеширование | Вернуть сохранённый ответ, если данные не изменились |
| 🌍 Версионирование API | `/api/v1/...` и `/api/v2/...` → разная логика |

> 💡 **Простыми словами:**  
> Ingress — это **«куда направить»**.  
> Gateway — это **«что сделать с запросом»**.

## 🧪 Пример из твоего проекта (код)

### 🔹 Ingress-правило (YAML):
```yaml
# "Запросы на /api/v1/gateway/* отправляй на gateway-service:8087"
- path: /api/v1/gateway
  pathType: Prefix
  backend:
    service:
      name: gateway-service
      port:
        number: 8087
```
→ Это просто **пересылка**. Ingress не смотрит, что внутри запроса.

### 🔹 Gateway-контроллер (Java, Spring Boot):
```java
// GatewayController.java
@GetMapping("/hotels")
public ResponseEntity<HotelsAavailabilityRes> getHotels(
    @RequestHeader("Authorization") String token,  // ← проверяем токен!
    @RequestParam String city) {                    // ← валидируем параметры
    
    // 1. Проверка токена (бизнес-логика!)
    if (!jwtProvider.validate(token)) {
        return ResponseEntity.status(401).build();
    }
    
    // 2. Запрос к hotel-service (агрегация!)
    HotelInfoRes hotels = hotelService.getHotels(city);
    
    // 3. Запрос к loyalty-service (ещё один сервис!)
    LoyaltyBalanceRes loyalty = loyaltyService.getBalance(token);
    
    // 4. Сборка единого ответа (трансформация!)
    return ResponseEntity.ok(new HotelsAavailabilityRes(hotels, loyalty));
}
```
→ Это **бизнес-логика**: проверка прав, вызов других сервисов, сборка ответа.

## 🧠 Коротко для запоминания

```
🔹 Ingress Controller = "шлагбаум" (инфраструктура)
   • Куда направить запрос? → сервис А или Б
   • Работает на уровне домена/пути/порта

🔹 Gateway Service = "консьерж" (бизнес-логика)
   • Что сделать с запросом? → проверить, агрегировать, трансформировать
   • Работает на уровне бизнес-сущностей: пользователь, отель, бронь

🔹 Вместе: Ingress → Gateway → Микросервисы
   • Ingress доставил запрос до нужного "подъезда"
   • Gateway решил, что с ним делать внутри "дома"
```

```markdown
### Архитектура обработки внешних запросов

В проекте используется двухуровневая маршрутизация:

1. **Ingress Controller (Nginx)** — инфраструктурный уровень:
   - Принимает внешние HTTPS-запросы на `app.10.174.8.95.nip.io:443`
   - Маршрутизирует по пути: `/api/v1/gateway/*` → `gateway-service:8087`
   - Обеспечивает TLS-терминацию (сертификат от cert-manager)

2. **Gateway Service (Spring Boot)** — прикладной уровень:
   - Проверяет JWT-токен в заголовке `Authorization`
   - Агрегирует данные из нескольких микросервисов:
     • hotel-service → информация об отелях
     • booking-service → статус брони
     • loyalty-service → баланс лояльности
   - Возвращает клиенту единый структурированный ответ

Такая архитектура позволяет:
• Изолировать инфраструктурную маршрутизацию от бизнес-логики
• Легко масштабировать каждый уровень независимо
• Менять реализацию Gateway без перенастройки Ingress
```

## ❓ Частые вопросы

**В: А можно ли обойтись без Gateway Service?**  
О: Да, если приложение простое. Можно направить Ingress напрямую на нужные сервисы. Но в микросервисной архитектуре Gateway — стандартный паттерн (API Gateway), который упрощает клиенту работу с системой.

**В: А можно ли обойтись без Ingress Controller?**  
О: Технически — да, если использовать `NodePort` или `LoadBalancer` для каждого сервиса. Но это неудобно: 7 сервисов = 7 внешних IP/портов, нет единой точки для TLS, логирования, лимитов.

**В: Почему в моём проекте Gateway Service называется `gateway-service`, а не `api-gateway`?**  
О: Это просто название. В разных проектах его называют по-разному: `api-gateway`, `edge-service`, `frontend-service`. Суть одна: точка входа в бизнес-логику.
