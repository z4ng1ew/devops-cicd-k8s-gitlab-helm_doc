чем деплоймент отличается от стейтфул сет ?



Deployment и StatefulSet — это контроллеры Kubernetes, но первый используется для stateless (не сохраняющих состояние) приложений, а второй — для stateful (сохраняющих состояние), таких как базы данных.





Главные отличия:

1) Идентичность подов: Поды в Deployment взаимозаменяемы и получают случайные имена. Поды в StatefulSet имеют строгие, порядковые имена (например, web-0, web-1), которые сохраняются при перезапусках.

2) Сетевые имена: В Deployment у каждого пода свой IP, который меняется при пересоздании. В StatefulSet каждый под получает постоянное DNS-имя, привязанное к его индексу.

3) Хранение данных: В Deployment поды используют общее хранилище (обычно ReadWriteMany). В StatefulSet для каждого пода создается свой уникальный PersistentVolumeClaim (PVC), обеспечивающий стабильную привязку данных.

4) Порядок работы: Deployment запускает и удаляет поды параллельно. StatefulSet работает строго последовательно (например, web-0 запустится и станет Ready до того, как начнется создание web-1).





















## 📦 Deployment vs StatefulSet — простыми словами

Представь разницу на примере **строительной бригады** и **номеров в отеле**:

| | **Deployment** | **StatefulSet** |
|---|---|---|
|  **Аналогия** |  Бригада рабочих: все в одинаковой форме, взаимозаменяемые. Если один ушёл — приходит другой с таким же инструментом. | 🏨 Номера в отеле: у каждого свой номер, свой ключ, своя история гостей. Вещи в номере привязаны именно к нему. |
| ️ **Имена подов** | Случайные: `gateway-5d4b6c7f9-x2k9m`, `gateway-5d4b6c7f9-m8p3q` | Упорядоченные: `postgres-0`, `postgres-1`, `postgres-2` |
| 💾 **Хранение данных** | Поды делят одно хранилище или не имеют своего. Данные не привязаны к конкретному поду. | **Каждый под получает свой личный диск (PVC)**. Данные "приклеены" к имени пода. |
| 🌐 **Сеть** | Все поды выходят в сеть через один общий Service. | У каждого пода свой стабильный DNS-адрес: `postgres-0.postgres-svc`, `postgres-1.postgres-svc` |
| 🔄 **Запуск / остановка** | Параллельно или в случайном порядке. | Строго по порядку: сначала `0`, потом `1`, потом `2`. При удалении — наоборот. |
| 🎯 **Для чего** | Веб-сервисы, API, фронты, микросервисы (без внутреннего состояния). | Базы данных, очереди сообщений, распределённые хранилища (где важно состояние). |

## 🎯 Что лучше для твоего случая?

Твой стек из проекта: **7 Java-микросервисов + PostgreSQL + RabbitMQ**.

| Компонент | Что выбрать | Почему |
|-----------|------------|--------|
| 🔹 **Java-сервисы** (gateway, session, hotel, booking, payment, loyalty, report) | ✅ **Deployment** | Они не хранят данные внутри себя. Всё состояние живёт в БД. Поды полностью взаимозаменяемы: упал один → поднялся другой → работает так же. |
| 🔹 **PostgreSQL** | ✅ **StatefulSet** | База данных *обязана* хранить файлы на диске. Если под упадёт и Kubernetes запустит его на другом узле, он должен найти **свои** данные, а не чужие. StatefulSet гарантирует, что `postgres-0` всегда получит свой PVC. |
| 🔹 **RabbitMQ** | ✅ **StatefulSet** (если кластер) или **Deployment** (если один инстанс) | Для учебного проекта часто хватает Deployment. Но если делаешь кластер из нескольких нод — StatefulSet, чтобы у каждой ноды был свой стабильный адрес и диск. |

## 🧠 Почему для БД именно StatefulSet?

1. **Данные привязаны к имени.** `postgres-0` → автоматически создаётся PVC `data-postgres-0`. Никакой путаницы при перезапуске.
2. **Порядок запуска.** БД должна подняться *до* сервисов, которые к ней подключаются. StatefulSet запускает поды по очереди (`0` → `1` → `2`), а не все сразу.
3. **Сетевая идентичность.** Другие сервисы могут обращаться к БД по стабильному адресу `postgres-0.postgres-svc`, а не по IP, который меняется при пересоздании пода.
4. **Безопасное масштабирование.** При уменьшении реплик StatefulSet удаляет поды в обратном порядке (`2` → `1` → `0`), чтобы не потерять данные с "старших" нод.

## 📝 Пример разницы в YAML (упрощённо)

```yaml
# ✅ Deployment (для Java-сервиса)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gateway-service
spec:
  replicas: 2
  template:
    spec:
      containers:
      - name: gateway
        image: твой_логин/do11-gateway:v1
        # Нет привязки к личному диску на уровне шаблона

---
# ✅ StatefulSet (для PostgreSQL)
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres-svc
  replicas: 1
  template:
    spec:
      containers:
      - name: postgres
        image: postgres:14-alpine
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:  # ← главная фишка StatefulSet
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 5Gi
```

> 💡 **Обрати внимание:** в StatefulSet не нужно создавать PVC вручную. Kubernetes сам создаст `data-postgres-0` при запуске `postgres-0`. Если под удалится и создастся заново — он автоматически подхватит тот же диск.
