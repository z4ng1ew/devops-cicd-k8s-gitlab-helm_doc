## 🧩 CRD (Custom Resource Definition) — простыми словами

**CRD** (Custom Resource Definition / Определение пользовательского ресурса) — это способ **научить Kubernetes новым типам объектов**, которых в нём изначально нет.

> 🧩 **Аналогия из жизни:**
> 
> Представь, что Kubernetes — это **конструктор LEGO** с базовым набором деталей:
> - 🧱 Стандартные детали: `Pod`, `Service`, `Deployment` (как кубики, окна, двери)
> - 🔧 **CRD** — это **инструкция, как сделать новую деталь** (например, «огнемет» или «лазер»)
> - После применения CRD ты можешь использовать эту новую деталь в своих постройках
>
> **cert-manager** устанавливает свои CRD → Kubernetes «учится» понимать новые объекты: `Certificate`, `Issuer`, `ClusterIssuer`.

---

## 🔍 Зачем вообще нужны CRD?

Kubernetes «из коробки» знает ограниченный набор объектов:

| Стандартные объекты (встроены) | Что делают |
|-------------------------------|-----------|
| `Pod` | Запускает контейнер |
| `Service` | Открывает доступ к поду |
| `Deployment` | Управляет репликами подов |
| `ConfigMap` | Хранит конфиги |
| `Secret` | Хранит секреты |

**Но что, если нужно больше?**

Например:
- 🔹 «Хочу объект `Certificate`, который сам запросит и обновит сертификат»
- 🔹 «Хочу объект `Database`, который сам поднимет кластер PostgreSQL»
- 🔹 «Хочу объект `Backup`, который по расписанию сделает снапшот»

**Ответ:** Создать **CRD** → описать, как выглядит новый объект → написать контроллер, который будет реагировать на его создание.

## 🔄 Как это работает в твоём проекте (cert-manager)

### Шаг 1: Устанавливаешь cert-manager
```bash
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.16.2/cert-manager.yaml
```

### Шаг 2: В кластер добавляются CRD
После установки ты можешь увидеть новые типы ресурсов:

```bash
kubectl get crd | grep cert-manager
```

Вывод (упрощённо):
```
certificates.cert-manager.io
clusterissuers.cert-manager.io
issuers.cert-manager.io
certificaterequests.cert-manager.io
challenges.acme.cert-manager.io
orders.acme.cert-manager.io
```

### Шаг 3: Теперь ты можешь создавать объекты этих типов
```yaml
# Это работает, потому что CRD уже зарегистрирован в кластере:
apiVersion: cert-manager.io/v1
kind: Certificate  # ← новый тип, которого не было в "чистом" Kubernetes
metadata:
  name: wildcard-nipio
spec:
  dnsNames:
    - "*.10.174.8.95.nip.io"
  issuerRef:
    name: my-ca-issuer
    kind: ClusterIssuer  # ← тоже новый тип!
```

### Шаг 4: Контроллер cert-manager «видит» твой объект и действует
```
Ты создаёшь Certificate
       │
       ▼
CRD говорит Kubernetes: «Это валидный объект, прими его»
       │
       ▼
Kubernetes сохраняет объект в etcd (своё хранилище)
       │
       ▼
Контроллер cert-manager видит: «О, новый Certificate! Надо выпустить сертификат»
       │
       ▼
Выполняет логику: запрашивает у Issuer → получает сертификат → кладёт в Secret
```

## 🧱 Из чего состоит CRD (упрощённо)

Когда ты смотришь на CRD, внутри него описано:

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition  # ← сам CRD — это тоже объект Kubernetes!
metadata:
  name: certificates.cert-manager.io
spec:
  group: cert-manager.io         # ← группа API (как "домен" для новых объектов)
  versions:                      # ← версии этого ресурса (v1, v1alpha1...)
    - name: v1
      served: true
      storage: true
  names:
    kind: Certificate            # ← как будет называться в YAML (kind: Certificate)
    plural: certificates         # ← множественное число для команд (kubectl get certificates)
    singular: certificate
  scope: Namespaced              # ← в каком неймспейсе работает (Namespaced или Cluster)
  versions: [...]
  # ... дальше схема полей (spec, status и т.д.)
```

> 💡 **Важно:** Ты **редко создаёшь CRD вручную**. Обычно они приходят вместе с инструментами (cert-manager, Prometheus Operator, Istio). Твоя задача — **использовать** объекты, которые эти CRD описывают.

## 🛠️ Практические команды для работы с CRD

```bash
# 1. Посмотреть ВСЕ установленные CRD в кластере:
kubectl get crd

# 2. Посмотреть детали конкретного CRD:
kubectl describe crd certificates.cert-manager.io

# 3. Посмотреть, какие объекты типа Certificate уже созданы:
kubectl get certificates -A  # -A = все неймспейсы

# 4. Посмотреть, как выглядит объект в "сыром" виде:
kubectl get certificate wildcard-nipio -o yaml

# 5. Удалить CRD (осторожно! это удалит возможность создавать такие объекты):
kubectl delete crd certificates.cert-manager.io
```

---

## ⚠️ Важные нюансы

| Нюанс | Почему это важно |
|-------|---------------|
| 🔹 **Удаление CRD ≠ удаление объектов** | Если удалить CRD, Kubernetes перестанет «понимать» эти объекты, но данные в etcd останутся. При повторной установке CRD — объекты «оживут». |
| 🔹 **Версионирование** | У CRD могут быть версии (`v1`, `v1beta1`). При обновлении инструмента (например, cert-manager) нужно следить за миграцией. |
| 🔹 **Права доступа (RBAC)** | Чтобы создавать объекты нового типа, у твоего пользователя/сервисного аккаунта должны быть права на этот ресурс. |
| 🔹 **Схема валидации** | В CRD можно описать, какие поля обязательны, какого они типа — это помогает ловить ошибки до применения манифеста. |

## 🧠 Коротко для запоминания

```
🔹 CRD = Custom Resource Definition = «инструкция, как добавить новый тип объекта в Kubernetes»
🔹 Позволяет расширять Kubernetes без изменения его исходного кода
🔹 cert-manager, Prometheus Operator, Istio — все используют CRD
🔹 Ты редко создаёшь CRD сам, чаще — используешь готовые (Certificate, Issuer и т.д.)
🔹 Команда: kubectl get crd — покажет все «расширения» твоего кластера
```

## 💡 Совет для отчёта

В `REPORT.MD` можно кратко пояснить:

```markdown
### CRD и cert-manager

При установке cert-manager в кластер регистрируются новые типы ресурсов (CRD):
- `Certificate` — описание сертификата, который нужно выпустить
- `Issuer` / `ClusterIssuer` — издатели сертификатов
- `CertificateRequest`, `Challenge`, `Order` — внутренние объекты для логики выпуска

Это позволяет декларативно управлять сертификатами:
```yaml
# Вместо ручного запуска openssl — просто создаём объект:
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: wildcard-nipio
spec:
  dnsNames: ["*.10.174.8.95.nip.io"]
  issuerRef: { name: my-ca-issuer, kind: ClusterIssuer }
```
Kubernetes принимает этот манифест благодаря CRD, а контроллер cert-manager 
выполняет всю сложную работу по выпуску и обновлению сертификата.
```

## 🎯 Почему это важно для твоего обучения и работы

1.  **Понимание архитектуры**: Большинство современных инструментов для Kubernetes (операторы, сервисные сетки, системы мониторинга) используют CRD. Знание этого механизма — ключ к работе с ними.
2.  **Отладка**: Если `kubectl apply` ругается «no matches for kind Certificate», значит, CRD не установлен или не загружен.
3.  **Безопасность**: Новые типы ресурсов = новые возможности = новые риски. Понимание, что ты устанавливаешь в кластер, критично.
4.  **Собеседования**: Вопрос «что такое CRD и зачем он нужен» — один из самых частых на позициях DevOps / Platform Engineer.
