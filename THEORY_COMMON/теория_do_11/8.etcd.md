## 🗄️ etcd — простыми словами

**etcd** (произносится «эт-си-ди») — это **распределённое надёжное хранилище «ключ-значение»**, где Kubernetes хранит **всё своё состояние** (конфигурацию кластера).

> 🧩 **Аналогия из жизни:**
> 
> Представь, что Kubernetes — это **большая компания**:
> 
> | Реальный мир | Мир Kubernetes |
> |-------------|---------------|
> | 🗄️ Архив с документами компании | **etcd** |
> | 📋 Приказ о найме сотрудника | Создание `Pod` |
> | 📋 Должностная инструкция | `Deployment` |
> | 📋 Пропуск в офис | `Service` / `Secret` |
> | 👔 Директор (читает архив) | `kube-apiserver` |
> 
> **etcd** — это единственный источник правды. Если архив сгорит — компания не знает, кто работает, какие есть должности и кому выданы пропуска.

---

## 🔑 Что именно хранится в etcd?

**Всё, что ты создаёшь через `kubectl`**:

```
etcd (упрощённо):
├── /registry/pods/default/my-pod → { "image": "nginx", "status": "Running" }
├── /registry/services/default/web → { "port": 80, "selector": { "app": "web" } }
├── /registry/deployments/default/app → { "replicas": 3, "template": {...} }
├── /registry/secrets/default/db-password → { "data": { "password": "****" } }
├── /registry/configmaps/default/app-config → { "data": { "DEBUG": "true" } }
├── /registry/nodes/k3s-worker1 → { "status": "Ready", "capacity": {...} }
└── ... и ещё сотни объектов
```

> 💡 **Важно:** etcd хранит только **декларативное состояние** (что ты *хочешь* видеть). Реальное состояние (что *фактически* работает) проверяют контроллеры Kubernetes.

---

## ⚙️ Ключевые свойства etcd (почему именно он?)

| Свойство | Что значит | Зачем это Kubernetes |
|----------|-----------|---------------------|
| 🔹 **Ключ-значение** (Key-Value) | Данные как в словаре: `ключ → значение` | Просто, быстро, предсказуемо |
| 🔹 **Распределённый** (Distributed) | Работает на нескольких серверах одновременно | Если один узел упадёт — данные не пропадут |
| 🔹 **Согласованный** (Consistent) | Все узлы видят **одинаковые** данные в один момент времени | Кластер принимает решения на основе актуальной информации |
| 🔹 **Надёжный** (Reliable) | Поддерживает репликацию и бэкапы | Состояние кластера — слишком ценно, чтобы его потерять |
| 🔹 **С поддержкой транзакций** | Можно атомарно изменить несколько ключей сразу | Безопасное обновление конфигураций |

## 🔄 Как etcd работает в твоём k3s-кластере

### Архитектура (упрощённо):

```
┌─────────────────────────────────┐
│         Твой k3s-кластер        │
│                                 │
│  ┌─────────────────────────┐   │
│  │   k3s-master (control)  │   │
│  │                         │   │
│  │  ┌─────────────────┐   │   │
│  │  │   kube-apiserver│◄──┼───┼── kubectl, контроллеры
│  │  └────────┬────────┘   │   │
│  │           │            │   │
│  │  ┌────────▼────────┐   │   │
│  │  │      etcd       │   │   │
│  │  │  (хранилище)    │   │   │
│  │  └─────────────────┘   │   │
│  └─────────────────────────┘   │
│                                 │
│  👷 Воркеры (k3s-worker1/2)    │
│  → получают задачи от API      │
└─────────────────────────────────┘
```

### Поток данных при создании пода:

```
1. Ты пишешь: kubectl apply -f pod.yaml
       │
       ▼
2. kube-apiserver принимает запрос, проверяет права
       │
       ▼
3. API записывает объект в etcd: /registry/pods/default/my-pod
       │
       ▼
4. etcd подтверждает: «Записал, данные сохранены»
       │
       ▼
5. kube-scheduler видит новый Pod без узла → назначает на worker1
       │
       ▼
6. kubelet на worker1 видит назначение → запускает контейнер
```

> ⚠️ **Без etcd этот процесс невозможен**: негде хранить состояние → кластер «забывает» всё при перезагрузке.

## 🛠️ Практика: как посмотреть данные в etcd (в k3s)

В k3s etcd работает в режиме **embedded** (встроен в процесс k3s), но данные можно посмотреть.

### 🔹 Способ 1: Через kubectl (безопасно и просто)

```bash
# Посмотреть все поды (данные берутся из etcd через API):
kubectl get pods -A

# Посмотреть конкретный объект в "сыром" виде:
kubectl get pod my-pod -o yaml

# Посмотреть, какие ресурсы занимают место:
kubectl api-resources
```

### 🔹 Способ 2: Прямой доступ к etcd (для продвинутых, осторожно!)

```bash
# На мастере: найти сертификаты для доступа к etcd
sudo ls /var/lib/rancher/k3s/server/tls/
# Нужны: etcd-server.crt, etcd-server.key, etcd-ca.crt

# Подключиться через etcdctl (утилита командной строки):
sudo k3s etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/var/lib/rancher/k3s/server/tls/etcd-ca.crt \
  --cert=/var/lib/rancher/k3s/server/tls/etcd-server.crt \
  --key=/var/lib/rancher/k3s/server/tls/etcd-server.key \
  get /registry/pods --prefix --keys-only | head -20
```

> ⚠️ **Не меняй данные в etcd вручную!** Это может «сломать» кластер. Только чтение для отладки.

## 💾 Бэкап etcd — почему это критично

Если etcd потеряет данные — **кластер придётся поднимать с нуля**.

### Как сделать бэкап в k3s:

```bash
# Остановить k3s (чтобы данные были консистентны):
sudo systemctl stop k3s

# Скопировать данные:
sudo cp -r /var/lib/rancher/k3s/server/db/etcd /backup/etcd-$(date +%F)

# Запустить обратно:
sudo systemctl start k3s
```

### Или «на лету» через snapshot (без остановки):

```bash
sudo k3s etcdctl snapshot save /backup/etcd-snapshot.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/var/lib/rancher/k3s/server/tls/etcd-ca.crt \
  --cert=/var/lib/rancher/k3s/server/tls/etcd-server.crt \
  --key=/var/lib/rancher/k3s/server/tls/etcd-server.key
```

## 🎯 Почему это важно знать тебе

| Причина | Как поможет |
|---------|------------|
| 🔹 **Отладка** | Если `kubectl` не видит объект — возможно, проблема в etcd или API |
| 🔹 **Безопасность** | Секреты хранятся в etcd (в base64) → важно шифровать etcd-at-rest в продакшене |
| 🔹 **Миграция** | При переносе кластера нужно перенести и etcd |
| 🔹 **Собеседования** | Вопрос «где Kubernetes хранит состояние?» — один из самых частых |
| 🔹 **Понимание архитектуры** | Без etcd нет Kubernetes — это фундамент |

## ❓ Частые вопросы

**В: А если etcd «упадёт» — что будет?**  
О: Кластер перестанет принимать изменения. Существующие поды продолжат работать, но создать новые или изменить конфигурацию будет нельзя.

**В: Почему не использовать обычную базу данных (PostgreSQL, MySQL)?**  
О: etcd оптимизирован под частые мелкие записи, согласованность и распределённость. SQL-базы не гарантируют такого уровня консистентности «из коробки».

**В: Можно ли заменить etcd на что-то другое?**  
О: В vanilla Kubernetes — нет, это жёсткая зависимость. В k3s есть экспериментальный режим с SQLite (`--datastore-endpoint`), но он только для тестов.
