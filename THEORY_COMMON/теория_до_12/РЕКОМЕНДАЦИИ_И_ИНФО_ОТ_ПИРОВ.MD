Argo CD — это декларативный инструмент для непрерывной доставки (CD) приложений в Kubernetes, работающий по методологии GitOps. Он синхронизирует состояние кластера с конфигурацией, описанной в вашем Git-репозитории.
## Как это работает

* Хранение в Git: Все манифесты Kubernetes (YAML, Helm-чарты, Kustomize) лежат в Git.
* Отслеживание изменений: Argo CD постоянно сравнивает желаемое состояние из Git с реальным состоянием в кластере.
* Автоматическая синхронизация: При обновлении кода в Git инструмент сам применяет изменения в Kubernetes.
* Устранение дрейфа: Если кто-то вручную изменит настройки в кластере, Argo CD вернет их к эталону из Git.

## Ключевые особенности

* Наглядный Web-интерфейс: Показывает дерево ресурсов приложения и статус их здоровья в реальном времени.
* Мультикластерность: Может управлять деплоем сразу во множество разных кластеров Kubernetes из одной панели.
* Безопасность: Доступ к кластеру имеет только сам Argo CD, разработчикам больше не нужны прямые права (kubectl) на прод-окружение.
* Легкий откат: Для возврата к старой версии приложения достаточно просто откатить коммит в Git.

# Пир ошибся технически, но ты слабо защитился

Распакую по полочкам — что правда, что нет, и как такие моменты отбивать в будущем.

---

## Что говорит официальная документация

`Service kubernetes` в namespace `default` — это **штатное поведение Kubernetes по умолчанию**, не только k3s. Так задумано **разработчиками самого Kubernetes**, и так работают **все дистрибутивы**: k3s, k8s, EKS, GKE, AKS, minikube, kind — везде одинаково.

Проверить можно прямо сейчас:

```bash
kubectl get svc -n default
```

На любом свежем кластере Kubernetes в мире увидишь **ровно одну строку**:
```
NAME         TYPE        CLUSTER-IP   EXTERNAL-IP   PORT(S)
kubernetes   ClusterIP   10.43.0.1    <none>        443/TCP
```

## Что это такое

`Service kubernetes` в `default` — это **доступ к API-серверу Kubernetes** изнутри кластера. Логика такая:

1. **API-сервер** (kube-apiserver) физически работает на мастер-ноде, слушает порт 6443. Это процесс, который принимает все команды управления кластером.

2. **Подам внутри кластера** иногда нужно обращаться к API-серверу — например, чтобы прочитать конфигурацию, посмотреть на других подов, обновить статус. Это делают: операторы, контроллеры (cert-manager, Prometheus Operator), ServiceAccount-токены.

3. Подам **неудобно** знать IP мастер-ноды напрямую — он может меняться, нод может быть несколько. Поэтому Kubernetes **сам создаёт** Service по имени `kubernetes` в namespace `default`, который указывает на API-сервер.

4. Дальше под просто обращается по адресу `https://kubernetes.default.svc.cluster.local` — CoreDNS резолвит это имя в ClusterIP сервиса, kube-proxy перенаправляет на реальный API-сервер.

То есть это **не «случайный остаток в default»**, а **сознательно сделанная точка входа к API**.

## Почему именно в `default`

Потому что **исторически** в Kubernetes namespace `default` — это «namespace для пользовательских ресурсов **по умолчанию**». Если ты `kubectl apply` без `-n`, оно попадает в `default`. И раз это «дефолтное место», там разместили **дефолтную** точку входа в API.

Альтернативой был бы `kube-system`, но создатели Kubernetes решили, что API должен быть доступен из любого namespace по одинаковому имени `kubernetes.default.svc` — это устойчивый контракт. Если бы Service лежал в `kube-system`, пришлось бы писать `kubernetes.kube-system.svc` — длиннее.

## Где пир был прав

В одном — частично. **Большинство** служебных компонентов k3s (CoreDNS, local-path-provisioner, metrics-server, Traefik если включён) действительно живут в **`kube-system`**. Это правда. Но **API-сервер исключение** — для него Service в `default` создаётся специально, и это требование самого Kubernetes, а не выбор k3s.

## Где пир ошибся

1. **«Дефолтные сервисы k3s находятся в неймспейсе k3s»** — неправда. **Нет такого namespace `k3s`**. Все системные компоненты k3s в `kube-system`. Проверь у себя:
   ```bash
   kubectl get namespaces
   ```
   Увидишь: `default`, `kube-system`, `kube-public`, `kube-node-lease` — стандартный набор Kubernetes. Никакого `k3s` нет.

2. **«Когда устанавливаешь k3s, в default пусто по умолчанию»** — тоже неправда. Service `kubernetes` появляется в `default` **сразу после установки** и **никогда не убирается**. Это часть базовой конфигурации Kubernetes — попытаешься удалить, контроллер пересоздаст через 10 секунд.

3. **«Сервис, который раздаёт IP-адреса»** — это уже **ты** немного запутался в ответе. `Service kubernetes` ничего не «раздаёт». IP-адреса для других Service'ов выдаёт **kube-controller-manager** (точнее, его компонент `service-ipallocator`). А Service `kubernetes` — это просто **точка входа к API**.

## Как надо было ответить

Когда пир спросил «почему он в дефолте?», правильный ответ был такой:

> «Service `kubernetes` в namespace `default` — это **точка входа к API-серверу Kubernetes** изнутри кластера. Подам нужно как-то обращаться к API (для cert-manager, операторов, ServiceAccount-токенов), и Kubernetes создаёт этот Service автоматически. Он размещён в `default` потому, что это namespace по умолчанию — любой под из любого namespace может обратиться по имени `kubernetes.default.svc.cluster.local`. Это **штатное поведение Kubernetes**, не специфика k3s — то же самое будет в EKS, GKE, любом дистрибутиве. Удалить его нельзя — control-plane тут же его пересоздаст.»

После этого можно было перейти в контратаку:

> «Кстати, ты упомянул namespace `k3s` — а покажешь, где он у тебя в кластере? У меня его нет. Все системные компоненты k3s в `kube-system`, как и в обычном Kubernetes.»

Это **переключает** разговор: теперь уже **пир должен** доказывать своё утверждение.

## 🟢 Замечание 1: «Свой образ PostgreSQL — а можно было через ConfigMap с init.sql»

**Пир прав на 100%.** Это **лучшая практика для PostgreSQL в k8s**.

### Как это правильно делается

Официальный образ `postgres:16-alpine` имеет встроенный механизм: всё, что положено в `/docker-entrypoint-initdb.d/`, **выполняется при первом запуске**. Можно положить туда:
- `*.sql` файлы — выполнятся как SQL
- `*.sh` скрипты — выполнятся как bash
- `*.sql.gz` — распакуются и выполнятся

Через ConfigMap это делается элегантно:

```yaml
# В overlays/production/01-configmap.yaml (или отдельным ConfigMap)
apiVersion: v1
kind: ConfigMap
metadata:
  name: postgres-init
data:
  init.sql: |
    CREATE DATABASE users_db;
    CREATE DATABASE hotels_db;
    CREATE DATABASE payments_db;
    CREATE DATABASE balances_db;
    CREATE DATABASE reservations_db;
    CREATE DATABASE statistics_db;
```

А в Deployment/StatefulSet PostgreSQL **монтируем** эту ConfigMap как файл:

```yaml
spec:
  containers:
    - name: postgres
      image: postgres:16-alpine     # стандартный образ, без пересборки
      volumeMounts:
        - name: init-script
```

2. **Автоматические обновления** — обновился базовый образ, ты просто меняешь тег и всё
3. **Прозрачность** — init-скрипт лежит в `git` как YAML, видно всё содержимое
4. **Размер** — не нужно тащить кастомный образ через `docker save/load`

## 🟢 Замечание 2: «pullPolicy: Never — а если забудешь собрать образ?»

**Пир прав концептуально, но твой контекст оправдан.**

### Что такое `imagePullPolicy`

| Значение | Поведение |
|---|---|
| `Always` | Всегда тянуть из реестра при создании пода |
| `IfNotPresent` | Тянуть, **только если** локально нет |
| `Never` | **Никогда** не тянуть — использовать только локальный |

### Где он прав

`Never` в production — **дыра**:
- Pod создаётся на новой ноде, где образа нет → `ImagePullBackOff`
- Масштабирование (HPA — Horizontal Pod Autoscaler — автомасштабирование) перестаёт работать
- Replacement пода после crash — лотерея

### Где ты прав

Для **учебной задачи в локальном кластере** без интернета у воркер-нод (или с медленным интернетом из России 2026) `Never` — **разумный компромисс**. Образы предзагружены через `k3s ctr images import`, выкачивать их из Docker Hub при каждом старте было бы абсурдом.

### Что нужно было ответить

> «Использовал `Never`, потому что образы предзагружены в containerd на всех нодах через `k3s ctr images import`. Это типичная практика для локальных кластеров и air-gapped (изолированных от интернета) environments. В production я бы использовал `IfNotPresent` с registry-доступом и конкретными версионными тегами.»

**Применить в следующих проектах:** для DO13/14 — да, лучше поднять private registry внутри кластера (Harbor, Distribution) и использовать `IfNotPresent`.

## 🔴 Замечание 3 (САМОЕ ВАЖНОЕ): «`latest` не использовать, нужны конкретные версии + digest»

**Пир абсолютно прав. Это критично.** Один из главных антипаттернов в индустрии.

### Почему `latest` — это плохо

1. **Невоспроизводимость**: сегодня `postgres:latest` это 16.4, завтра 17.0 — твоё приложение может сломаться без единого изменения в коде.

2. **Замена с тем же тегом**: разработчик зафиксил баг и **перезалил образ под тем же тегом** `latest`. У тебя локально старая версия — внутри она другая. Ты этого не заметишь до прода.

3. **Безопасность**: атакующий захватил аккаунт мейнтейнера → перезалил `latest` с трояном → твой кластер качает заражённый образ. С хешем такого не случится.

4. **Откат невозможен**: к чему откатываться-то? «Latest» — это не точка во времени, это «то что сейчас в реестре».

### Как делать правильно

```yaml
# Плохо
image: postgres:latest

# Лучше
image: postgres:16.4-alpine

# Идеально (immutable image — неизменяемый образ)
image: postgres:16.4-alpine@sha256:abc123def456...
```

**Digest** (дайджест) — это SHA256-хеш **содержимого образа**. Он гарантирует, что ты получаешь **точно тот** образ, что ожидаешь. Даже если кто-то перезальёт `postgres:16.4-alpine` под тем же тегом, digest изменится — и Kubernetes откажется его тянуть.

Получить digest можно так:
```bash
docker pull postgres:16.4-alpine
docker inspect postgres:16.4-alpine | grep -i 'RepoDigests' -A 2
```

### Что нужно было ответить

> «Ты прав, `latest` в production — антипаттерн. Конкретные версии гарантируют воспроизводимость, digest даёт криптографическую защиту от подмены — если разработчик перезаливает образ под тем же тегом (фикс бага без bump'а версии), digest изменится и Kubernetes это поймает. В следующих проектах перейду на схему `tag@sha256:...`.»

**Применить в следующих проектах: ОБЯЗАТЕЛЬНО.** Это один из самых частых вопросов на собеседованиях DevOps.

### Дополнение про управление версиями

В реальных компаниях для образов делают **CI/CD-пайплайны**, которые автоматически:
1. Собирают образ с тегом `<repo>:<git-sha>` (например, `myapp:a3b8f9c`)
2. Пушат в private registry
3. Обновляют тег в манифесте через `kustomize edit set image` или `helm upgrade --set image.tag=...`

Никаких `latest` нигде.

## 🟢 Замечание 4: «Что такое `management` у RabbitMQ?»

**Пир прав, ты ответил неточно.**

### Что значит `management`

В именах образов RabbitMQ суффикс `-management` означает наличие **встроенного веб-интерфейса** на порту 15672. Через него можно:
- Смотреть очереди и сообщения в них
- Создавать exchanges, queues, bindings
- Управлять пользователями и правами
- Видеть нагрузку и графики

Образ **без** `-management` (просто `rabbitmq:3.12-alpine`) — это только AMQP-брокер на 5672. Веба нет, всё управление через CLI (`rabbitmqctl`).

### Сравнение тегов RabbitMQ

| Тег | Что включено | Размер |
|---|---|---|
| `rabbitmq:3.12` | AMQP-сервер на Debian | ~250 МБ |
| `rabbitmq:3.12-alpine` | AMQP-сервер на Alpine | ~150 МБ |
| `rabbitmq:3.12-management` | + Web UI на Debian | ~280 МБ |
| `rabbitmq:3.12-management-alpine` | + Web UI на Alpine | ~170 МБ |

То есть отличия не «наличие веб-интерфейса» (как сказал пир), а **комбинации**:
- `-management` = веб-интерфейс
- `-alpine` = базовый образ Alpine вместо Debian

### Что нужно было ответить

> «`management` — это включённый плагин `rabbitmq_management` с веб-интерфейсом на порту 15672 и REST API для управления. Я выбрал именно эту версию, чтобы можно было визуально смотреть очереди и отлаживать межсервисное взаимодействие. Суффикс `-alpine` — это базовый образ Alpine Linux вместо Debian, в 2 раза меньше по размеру.»

## 🔴 Замечание 5 (КРИТИЧНО): «Значения секретов должны быть в values.yaml, а не в манифесте»

**Пир абсолютно прав. Это твой главный архитектурный недочёт в Helm-чарте.**

### Что у тебя сейчас (плохо)

В `templates/02-secrets.yaml`:
```yaml
data:
  POSTGRES_USER: cG9zdGdyZXM=       # захардкоженный base64 от "postgres"
  POSTGRES_PASSWORD: cG9zdGdyZXM=
```

Чтобы поменять пароль, нужно:
1. Открыть файл
2. Перекодировать в base64
3. Закоммитить **секрет** в git (катастрофа для безопасности!)
4. Пересобрать чарт

### Как правильно

В `values.yaml`:
```yaml
secrets:
  postgres:
    user: "postgres"
    password: "postgres"   # значение по умолчанию для dev
  rabbitmq:
    user: "guest"
    password: "guest"
```

В `templates/02-secrets.yaml`:
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: app-secrets
type: Opaque
stringData:
  POSTGRES_USER: {{ .Values.secrets.postgres.user | quote }}
  POSTGRES_PASSWORD: {{ .Values.secrets.postgres.password | quote }}
  RABBIT_MQ_USER: {{ .Values.secrets.rabbitmq.user | quote }}
  RABBIT_MQ_PASSWORD: {{ .Values.secrets.rabbitmq.password | quote }}
```

`stringData` (строковые данные) — это поле Secret, куда можно класть значения **в открытом виде**. Kubernetes сам закодирует их в base64. Удобнее, чем `data` с ручным `base64`.

### А что насчёт «рандомных значений по умолчанию»

Это **прикольная фишка** Helm, про которую сказал пир. Используется функция `randAlphaNum`:

```yaml
stringData:
  POSTGRES_PASSWORD: {{ .Values.secrets.postgres.password | default (randAlphaNum 16) | quote }}
```

Логика: если в `values.yaml` пароль **передан** — используем его. Если **не передан** — Helm сгенерирует случайный 16-символьный.

**Подвох**: при каждом `helm upgrade` без явного значения генерируется **новый** пароль → приложение ломается, потому что postgres ожидает старый. Чтобы это исправить, нужно использовать `lookup` — функцию, которая читает уже существующий Secret в кластере:

```yaml
# Сохраняем существующий пароль, генерируем новый только если Secret не существует
{{- $existingSecret := lookup "v1" "Secret" .Release.Namespace "app-secrets" }}
{{- if $existingSecret }}
  POSTGRES_PASSWORD: {{ index $existingSecret.data "POSTGRES_PASSWORD" }}  # старое значение
{{- else }}
  POSTGRES_PASSWORD: {{ .Values.secrets.postgres.password | default (randAlphaNum 16) | b64enc }}
{{- end }}
```

Это уже high-level Helm, но **знать о таких возможностях надо**.

### Что нужно было ответить

> «Согласен, это слабое место. У меня значения захардкожены в Secret-манифесте. Правильно — вынести в `values.yaml` с возможностью переопределения через `--set` или отдельный `values-prod.yaml`. Знаю про функцию `randAlphaNum` для генерации дефолтных паролей и `lookup` для сохранения значений между обновлениями. В DO13/14 перепишу.»

**Применить в следующих проектах: ОБЯЗАТЕЛЬНО.** Это buy-in пира на 100%.
