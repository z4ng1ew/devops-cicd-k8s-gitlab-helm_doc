Helm — менеджер пакетов для Kubernetes. Использует шаблонизацию: 
в манифестах ставится `{{ .Values.x }}`, а в values.yaml задаются 
значения. При установке Helm рендерит шаблоны и применяет к кластеру.









### 🎓 Helm для защиты проекта: полный гайд простыми словами

Ниже — всё, что нужно знать, чтобы уверенно ответить на вопросы проверяющего (пира/ментора). Объясняю **простыми словами**, сложные термины расшифровываю.

## 1. Что такое Helm? (ответ на вопрос «зачем это нужно»)

> **Helm (Хелм)** — это «менеджер пакетов» (как `apt` в Linux или `pip` в Python), но для **Kubernetes**.

**Проблема без Helm:**
- Чтобы запустить приложение в Kubernetes, нужно создать 5–10 YAML-файлов: `deployment.yaml`, `service.yaml`, `configmap.yaml`, `secret.yaml`, `ingress.yaml` и т.д.
- Если нужно запустить то же приложение в другой среде (например, не `prod`, а `stage`), приходится копировать файлы и менять в них значения вручную → легко ошибиться.

**Решение с Helm:**
- Все эти YAML-файлы упаковываются в один **Chart (чарт)** — как «архив с инструкциями».
- В чарте есть файл `values.yaml` — там хранятся настройки (например, `replicaCount: 3`).
- В шаблонах пишешь `{{ .Values.replicaCount }}` — и при установке Helm сам подставит нужное значение.
- Одна команда `helm install` — и всё приложение развёрнуто в кластере.

🔹 **Простая аналогия**: Helm — это как «установщик программы» (.exe), где ты выбираешь галочки (настройки), а установщик сам всё раскладывает по папкам.

## 2. Ключевые понятия (обязательно знать для защиты)

| Термин | Простыми словами | Пример / Зачем нужен |
|--------|-----------------|---------------------|
| **Chart (чарт)** | Папка с шаблонами и настройками для развёртывания приложения | Как «инструкция + детали» для сборки приложения в Kubernetes |
| **Release (релиз)** | Конкретный запуск чарта в кластере с именем | `helm install my-app ./chart` → создаст релиз с именем `my-app` |
| **Repository (репозиторий)** | Хранилище чартов (как Docker Hub, но для Helm) | Можно хранить свои чарты или использовать публичные (Bitnami, Prometheus) |
| **Template (шаблон)** | YAML-файл с «дырками» `{{ .Values.x }}`, которые заполняются при установке | Позволяет использовать один файл для dev/prod/stage |
| **Values.yaml** | Файл с настройками: сколько реплик, какой образ, порты и т.д. | Меняешь только этот файл — не трогаешь шаблоны |
| **Go Template** | Язык шаблонизации внутри Helm (от языка Go) | Синтаксис `{{ if .Values.debug }}...{{ end }}` для условий |

## 3. Как работает Helm: пошагово

```
1. Ты пишешь шаблоны в папке templates/
   → deployment.yaml: 
     replicas: {{ .Values.replicaCount }}

2. Задаёшь значения в values.yaml:
   → replicaCount: 3

3. Запускаешь: helm install my-release ./my-chart

4. Helm делает:
   ✅ Читает values.yaml
   ✅ Подставляет значения в шаблоны (рендеринг)
   ✅ Получает «чистые» YAML-манифесты
   ✅ Отправляет их в Kubernetes через kubectl

5. Результат: в кластере появилось приложение
```

🔹 **Важно**: Helm не меняет исходные шаблоны — он создаёт «временные» манифесты на лету.

## 4. Основные команды (что и зачем вводить)

| Команда | Что делает | Когда использовать |
|---------|-----------|-------------------|
| `helm create <name>` | Создаёт структуру чарта с примерами | В начале проекта |
| `helm lint <chart>` | Проверяет чарт на ошибки | Перед установкой |
| `helm install <name> <chart>` | Устанавливает приложение в кластер | Первый запуск |
| `helm status <name>` | Показывает статус релиза | Проверка, всё ли работает |
| `helm upgrade <name> <chart>` | Обновляет приложение новыми настройками | После изменения values.yaml |
| `helm rollback <name> <revision>` | Откатывает релиз к предыдущей версии | Если после обновления что-то сломалось |
| `helm uninstall <name>` | Удаляет приложение из кластера | Очистка |
| `helm template <chart>` | Показывает, какие манифесты сгенерирует Helm (без применения) | Отладка, проверка |
| `helm package <chart>` | Упаковывает чарт в `.tgz`-архив | Для публикации в репозиторий |

## 5. Шаблонизация: как читать и писать `{{ .Values.x }}`

**Базовый синтаксис (не бойся — это просто):**

```yaml
# В templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Values.appName }}  # ← подставит значение из values.yaml
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
      - name: {{ .Chart.Name }}  # ← имя чарта из Chart.yaml
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

```yaml
# В values.yaml
appName: my-gateway
replicaCount: 3
image:
  repository: nginx
  tag: "1.25"
```

**Результат после рендеринга (что уйдёт в Kubernetes):**
```yaml
metadata:
  name: my-gateway
spec:
  replicas: 3
  ...
  containers:
  - name: k8s-helm-kustomize-deploy
    image: "nginx:1.25"
```

🔹 **Условия и циклы** (если спросят продвинутое):
```yaml
# Если включен debug-режим — добавляем переменную окружения
{{- if .Values.debug }}
env:
  - name: DEBUG_MODE
    value: "true"
{{- end }}

# Если несколько портов — генерируем список
{{- range .Values.ports }}
- containerPort: {{ . }}
{{- end }}
```

## 6. Преимущества Helm (почему его используют в продакшене)

✅ **Повторяемость**: один чарт — работает везде (dev, stage, prod)  
✅ **Версионирование**: у каждого релиза есть номер, можно откатиться  
✅ **Зависимости**: чарт может зависеть от других чартов (например, твоему приложению нужна PostgreSQL — Helm сам её поставит)  
✅ **Безопасность**: секреты и конфиги вынесены в values.yaml, можно использовать разные файлы под разные среды  
✅ **Автоматизация**: легко встраивается в CI/CD (GitLab CI, GitHub Actions)

## 7. Частые вопросы на защите (и как на них отвечать)

### ❓ «Зачем Helm, если есть Kustomize?»
> «Kustomize хорош, когда у вас уже есть готовые YAML-манифесты и нужно их слегка изменить под среду. Helm лучше, когда нужно **упаковать приложение как продукт**: с зависимостями, версионированием, возможностью легко ставить/обновлять/удалять. В этом проекте я использовал оба инструмента, чтобы сравнить подходы: Kustomize — для наложений (overlays), Helm — для пакетной доставки.»

### ❓ «Что будет, если изменить values.yaml и не сделать upgrade?»
> «Ничего не изменится в кластере. `values.yaml` — это просто файл на твоём компьютере. Чтобы изменения применились, нужно выполнить `helm upgrade`. Это как изменить конфиг-файл программы, но не перезапустить её.»

### ❓ «Где хранятся секреты в Helm?»
> «В `values.yaml` можно писать секреты, но это небезопасно, если файл попадает в репозиторий. Лучше:  
> - использовать отдельный файл `values-secret.yaml` и добавить его в `.gitignore`,  
> - или хранить секреты во внешнем хранилище (HashiCorp Vault),  
> - или использовать `helm install --set-file secretKey=./key.txt`.»

### ❓ «Как откатить ошибку после обновления?»
> «Команда `helm rollback <release-name> <revision>`. Helm хранит историю релизов: `helm history my-app` покажет все версии. Можно откатиться на шаг назад или на любую предыдущую версию.»

### ❓ «Можно ли использовать Helm без шаблонов?»
> «Технически — да, можно положить готовые YAML в папку `templates/` без `{{ }}`. Но тогда теряется смысл шаблонизации. Лучше использовать шаблоны хотя бы для имени приложения и количества реплик — это даёт гибкость.»

## 8. Шпаргалка для быстрого повторения перед защитой

```
🔹 Helm = пакетный менеджер для K8s
🔹 Chart = папка с шаблонами + values.yaml + Chart.yaml
🔹 Release = запущенный экземпляр чарта в кластере
🔹 {{ .Values.x }} = подстановка из values.yaml
🔹 helm install / upgrade / rollback / uninstall = основные команды
🔹 Преимущества: повторяемость, версионирование, зависимости, автоматизация
🔹 Безопасность: не хранить секреты в основном values.yaml, использовать --set-file или внешние хранилища
```
